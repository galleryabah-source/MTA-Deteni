Status: RECONCILIATION IN PROGRESS / MIGRATION FREEZE = TRUE

## Canonical source selected

The live production contract is authoritative for vocabulary and state transitions. The repository must not introduce a third outbox model.

Canonical production fields:

- event_id
- event_type
- aggregate_type
- aggregate_id
- payload
- idempotency_key
- occurred_at
- status
- attempts
- available_at

Canonical lifecycle:

`PENDING → PROCESSING → PUBLISHED`

Retry:

`PROCESSING → PENDING`

The application contracts now use these production names and statuses.

## Reconciled gaps

### 1. Status vocabulary

The former `outbox-contract.ts` used `PENDING | PUBLISHED | FAILED`, while the runtime contract used `PENDING | DISPATCHED | FAILED`.

Both were inconsistent with the live dispatcher boundary. The canonical status set is now:

`PENDING | PROCESSING | PUBLISHED | FAILED`

`FAILED` is retained because it is a live schema state, while the current dispatcher retry path normally returns a processing event to `PENDING`.

### 2. Attempt and lease vocabulary

The canonical fields are `attempts`, `availableAt`, `lockedAt`, `publishedAt`, and `lastError`.

`attemptCount` and `DISPATCHED` are not canonical P9.8 production vocabulary.

### 3. Execution context

Request/correlation/actor identity is carried by the outbox payload in the deployed production path. The application runtime contract may retain `ExecutionContext` as a type-level boundary, but its idempotency key must equal the persisted `idempotency_key`. It is not a second persistence model.

## Dispatcher reconciliation

The historically deployed dispatcher source is now restored under:

`supabase/functions/mta-outbox-dispatcher/index.ts`

It uses the live service-role RPC boundary:

- `claim_outbox_events`
- `complete_outbox_event`
- `release_outbox_event`

It does not directly mutate `mta_internal.outbox_events`.

## Lease finding

The dispatcher passes `p_lease_seconds` to the claim RPC. The production claim implementation observed during forensic audit records `locked_at` but does not use that parameter to calculate an expiry in the claim path.

This is a real reconciliation item. It is not being silently corrected while `MIGRATION_FREEZE = TRUE`.

Required next treatment: deterministic regression must model and evidence the currently deployed claim/release semantics first; any lease-expiry hardening requires a separately governed repository change and, only if later approved, a migration window.
