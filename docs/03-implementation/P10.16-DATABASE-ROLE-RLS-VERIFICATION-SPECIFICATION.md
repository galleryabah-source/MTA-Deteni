# P10.16 — Database Role/RLS Verification Specification

## Status

PREPARED — synthetic verification specification only. Execution remains blocked while `MIGRATION_FREEZE=TRUE`.

## Verification principle

Application authorization remains authoritative. PostgreSQL RLS and privileges are defense-in-depth. No test may weaken RLS, grant browser write access, or substitute a permissive policy merely to make a test pass.

## Synthetic role matrix

| Role/context | Expected grant read | Expected grant insert | Expected consume/revoke |
|---|---:|---:|---:|
| anonymous/public | DENY | DENY | DENY |
| authenticated without approved scope | DENY | DENY | DENY |
| authenticated wrong scope | DENY | DENY | DENY |
| authenticated inactive/revoked actor | DENY | DENY | DENY |
| authorized server actor + approved scope | ALLOW via server boundary | ALLOW via server boundary | ALLOW when lifecycle predicates match |
| Super Admin without operational authority | DENY | DENY | DENY |

## Synthetic fixtures

Fixtures must contain opaque IDs only, for example `actor-test-001`, `scope-test-A`, `object-test-001`, `grant-test-001`. They must never contain detainee names, document contents, health information or production identifiers.

Required fixture dimensions:

- active vs revoked actor;
- approved vs wrong scope;
- matching vs mismatched object;
- active vs expired grant;
- ACTIVE vs CONSUMED vs REVOKED lifecycle;
- single-use vs replay attempt.

## Post-migration checks

After authorized execution, verify independently:

1. target database identity;
2. table existence and exact columns;
3. lifecycle/checksum/expiry constraints;
4. required indexes;
5. RLS enabled;
6. no unintended anon/public/authenticated table privileges;
7. no browser-direct write path;
8. actor/scope/object isolation;
9. atomic consume and revoke affected-row semantics;
10. transaction/audit/outbox consistency;
11. concurrent consume produces exactly one terminal success;
12. evidence is persisted without sensitive payloads.

## Hard stops

A verification run must terminate as `SKIPPED_BY_SAFETY_GATE` or `BLOCKED` if freeze remains active, target identity differs, required approval is absent, fixtures are not synthetic, RLS is disabled, unexpected privileges exist, or evidence cannot be persisted safely.

No failure may be converted to PASS by changing the test expectations or weakening the database policy.
