# P10.3 — Movement Ledger / Headcount

## Status

Executable foundation implemented. Certification remains **NOT CERTIFIED** until the repository CI evidence is independently green and the real persistence/concurrency boundary is verified.

## Scope

P10.3 introduces an append-only movement ledger and a deterministic headcount projection without changing the database schema.

Flow:

`Request Context → Authorization → Movement Validation → Append-only Ledger → Transaction → Audit → Outbox → Headcount Projection`

## Invariants

1. Movement events are append-only and sequenced.
2. A request ID is idempotent for the ledger; replay does not create a second event.
3. Movement requires explicit detainee, actor, scope, request and correlation context.
4. Only the `ACTIVE` synthetic lifecycle state is eligible for this boundary.
5. Headcount is derived from the latest known placement per detainee rather than maintained as an independently writable counter.
6. Authorization remains deny-by-default and occurs before transactional mutation.
7. Critical mutation, audit and outbox are committed through the existing transactional test boundary.
8. AI remains OFF and all fixtures are synthetic.

## Deliberate non-claims

The current ledger is an in-memory executable boundary. It does not prove PostgreSQL transaction isolation, database-level capacity enforcement, row locking, durable sequence allocation, or production headcount reconciliation. Those remain implementation gates before production use.

No migration is introduced by P10.3.

## Test contract

`test/p10.3-movement-ledger-headcount.test.mjs` covers append-only sequencing, replay behavior, invalid state rejection, headcount reconstruction, authorization denial, atomic audit/outbox side effects, and mandatory request context.
