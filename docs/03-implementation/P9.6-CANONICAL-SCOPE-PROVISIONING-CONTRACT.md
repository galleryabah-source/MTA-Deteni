# P9.6 — Canonical Scope Provisioning Contract v1

## Purpose

Define a controlled contract for provisioning an operational scope and explicit OWNER/ADMIN memberships after the database schema contract has been reconciled.

## Evidence boundary

The production-applied canonical-scope migration establishes:

- `mta_scopes` as the authorization scope registry;
- `mta_profile_scopes` as the profile-to-scope membership relation;
- one explicit operational scope on each detainee;
- access through active `mta_profile_scopes` membership.

The production migration **does not define a canonical scope code or name**, and the current production database contains no scope rows. Therefore this contract intentionally does not invent a scope identity.

## Provisioning input

```json
{
  "scope": {
    "code": "<EXPLICIT-GOVERNED-CODE>",
    "name": "<EXPLICIT-GOVERNED-NAME>",
    "active": true
  },
  "assignments": [
    {
      "profileId": "<EXPLICIT-PROFILE-ID>",
      "expectedRole": "OWNER",
      "active": true
    },
    {
      "profileId": "<EXPLICIT-PROFILE-ID>",
      "expectedRole": "ADMIN",
      "active": true
    }
  ]
}
```

The placeholders above are **contract placeholders, not seed values**.

## Required controls

1. Scope `code` is explicit and unique.
2. Scope `name` is explicit.
3. Scope identity is never inferred from `role`.
4. Every assignment identifies an explicit `profileId`.
5. `expectedRole` is restricted to `OWNER` or `ADMIN`.
6. The provisioning transaction must re-read `mta_profiles.role` and reject role drift.
7. Only active memberships are provisioned by this contract.
8. Duplicate profile membership is rejected.
9. Existing conflicting scope membership must be detected before mutation.
10. Scope creation and membership assignment are one transaction.
11. The provisioning operation must be auditable.
12. Production execution is prohibited until governance clearance lifts `MIGRATION_FREEZE`.

## Explicit non-goals

This contract does not:

- create scope rows in production;
- assign production OWNER/ADMIN users;
- infer a facility/site name;
- map every role automatically to a scope;
- bypass `SCOPE_REQUIRED`;
- alter RLS;
- make `OWNER` or `ADMIN` intrinsically scoped without membership.

## Important semantic distinction

The historical migration says:

> one explicit operational scope per detainee

That is **not evidence that production has exactly one global scope**.

Therefore the provisioning contract does not impose a global single-scope invariant. If governance later decides that MTA DETENI production must have exactly one scope, that must be recorded as an explicit application/data invariant before provisioning.

## Promotion path

```text
source-of-truth scope identity
        ↓
governed provisioning manifest
        ↓
manifest validation
        ↓
nonprod transactional provisioning
        ↓
positive + negative authorization tests
        ↓
P9.6 final certification
        ↓
governance review
        ↓
only then evaluate production reconciliation
```
