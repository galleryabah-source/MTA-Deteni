# MTA DETENI — P9.10 Health + Observability Kernel v1.0

## Status
CONTRACT COMPLETE / IMPLEMENTATION NOT VERIFIED / MIGRATION FREEZE = TRUE / PRODUCTION = NO-GO

## Objective
Provide reliable health, readiness, telemetry, logging, correlation, metrics, and operational diagnostics without exposing protected detainee data, credentials, tokens, or sensitive business payloads.

Observability is an operational control layer. It is not a substitute for audit, authorization, reconciliation, or domain state.

## Architectural boundary
```text
Request / Worker
      |
      +--> Request ID
      +--> Correlation ID
      +--> Structured Logs
      +--> Metrics
      +--> Traces (optional)
      |
      v
Observability Layer
      |
      +--> Health / Readiness
      +--> Dependency Status
      +--> Alerting
      +--> Operational Dashboard
```

## Health model
Health must distinguish system availability from business correctness.

Recommended dependency classes:
- `CORE`
- `DATABASE`
- `AUTH`
- `STORAGE`
- `OUTBOX`
- `NOTIFICATION`
- `DOCUMENT`
- `AI_OPTIONAL`

AI must never make overall core readiness fail when AI is intentionally disabled.

## Endpoints

### Liveness
`GET /api/health/live`

Purpose: determine whether the process is alive and able to answer requests.

Liveness must not perform expensive dependency checks.

### Readiness
`GET /api/health/ready`

Purpose: determine whether the service is ready to accept traffic for the declared environment.

Readiness may check critical dependencies such as database connectivity/configuration and required initialization state.

A dependency marked optional must not block readiness when intentionally disabled.

### Detailed health
`GET /api/health`

Authorized operational endpoint. May expose dependency/component status subject to policy.

Do not expose secrets, connection strings, internal tokens, raw SQL errors, storage credentials, provider credentials, or sensitive detainee data.

## Health response contract
```ts
export type HealthStatus = "UP" | "DEGRADED" | "DOWN" | "DISABLED";

export type ComponentHealth = {
  component: string;
  status: HealthStatus;
  latencyMs?: number;
  checkedAt: string;
  version?: string;
  reasonCode?: string;
};

export type HealthResponse = {
  status: "UP" | "DEGRADED" | "DOWN";
  appVersion: string;
  environment: string;
  checkedAt: string;
  components: ComponentHealth[];
  correlationId: string;
};
```

The response must use allowlisted fields only.

## Dependency rules

| Dependency | Criticality | Failure behavior |
|---|---|---|
| CORE process | Critical | readiness fails if unavailable |
| DATABASE | Critical | readiness fails for operations requiring DB |
| AUTH | Critical | protected operations fail closed |
| STORAGE | Critical for file operations | file operations fail safely; core read operations may remain available according to policy |
| OUTBOX | Critical for guaranteed asynchronous effects | health degraded; required transactional outbox writes fail safely |
| NOTIFICATION | Non-core external dependency | domain transaction remains valid; notification becomes failed/retry state |
| DOCUMENT | Domain-dependent | source transaction remains authoritative; document job retries/fails safely |
| AI | Optional | must not block core operation |

## Request context
Every request should have:
```ts
export type RequestContext = {
  requestId: string;
  correlationId: string;
  actorId?: string;
  scope?: string;
  policyVersion?: string;
};
```

Rules:
- generate a request ID if absent;
- validate inbound IDs and prevent header injection;
- propagate correlation ID through application services, transactions, outbox events, document/notification jobs, and audit events;
- do not place sensitive data inside correlation IDs;
- preserve causation/correlation relationships for asynchronous processing.

## Structured logging
Logs must be machine-readable and schema-controlled.

Recommended fields:
```text
level
service
version
environment
timestamp
request_id
correlation_id
actor_id (when policy permits)
action
component
result
error_code
latency_ms
```

Never log:
- passwords;
- session secrets;
- access/refresh tokens;
- signed download URLs;
- API keys;
- database connection strings;
- raw detainee health data;
- raw document contents;
- full highly restricted payloads;
- complete WhatsApp messages when they contain protected information.

Sensitive identifiers should be minimized or pseudonymized in operational logs where practical.

## Error observability
Internal errors must be mapped to stable application error codes.

Client response:
```json
{
  "success": false,
  "error": {
    "code": "STABLE_ERROR_CODE",
    "message": "Safe user-facing message"
  },
  "correlationId": "..."
}
```

Do not return stack traces, SQL fragments, filesystem paths, provider secrets, or internal object-storage keys to clients.

## Metrics
Baseline metrics:

### Application
- request count;
- request latency;
- error count/rate;
- HTTP status distribution;
- rate-limit events;
- validation failures;
- authorization denials.

### Database
- connection pool utilization;
- query latency buckets;
- connection failures;
- transaction failures;
- transaction duration;
- deadlock/serialization failures where available.

### Authorization/security
- authentication failures;
- authorization denials by reason code;
- scope denials;
- CSRF/CORS rejection counts;
- rate-limit rejection counts;
- suspicious request-pattern counters without storing sensitive payloads.

### Audit
- audit write success/failure;
- audit verification status;
- audit queue/backlog if asynchronous components are used;
- integrity verification failures.

### Outbox/workers
- pending count;
- processing count;
- retry count;
- dead-letter count;
- oldest pending age;
- processing latency;
- stale lease count;
- worker heartbeat status.

### Storage
- upload count/failure rate;
- quarantine count;
- integrity-check failures;
- download denial rate;
- provider latency/errors;
- orphan-object findings.

### Notification
- queued/sent/delivered/read/failed counts;
- provider latency;
- retry/dead-letter counts;
- no-recipient events;
- acknowledgement latency.

### AI optional
- enabled/disabled state;
- request count;
- latency;
- timeout/error count;
- policy denials;
- but no raw prompt/response content in ordinary metrics.

AI metrics must never become a prerequisite for core readiness.

## Business-sensitive telemetry
Operational telemetry must not create a shadow source of truth.

Examples:
- dashboard metrics describe canonical data but do not replace it;
- a counter of completed leave is not itself evidence of completion;
- an authorization-denial metric is not proof of misconduct;
- an overdue metric is not a legal violation conclusion;
- a notification delivery metric is not acknowledgement.

## Alerting
Alerts should be policy-driven and actionable.

Recommended alert classes:
- database unavailable;
- authentication service unavailable;
- audit integrity verification failure;
- sustained outbox backlog;
- dead-letter growth;
- storage integrity failure;
- notification provider outage;
- repeated authorization infrastructure failure;
- worker failure/stale leases;
- backup/recovery test failure where telemetry is available.

AI provider outage should normally be informational/degraded, not a core production outage, when AI is optional.

## Security and privacy
Observability systems are themselves sensitive.

Controls:
- least-privilege access;
- separate operational logs from business audit;
- retention policy for logs/metrics/traces;
- restricted log search/export;
- no unrestricted query endpoint;
- encryption in transit/at rest where applicable;
- audit access to sensitive operational telemetry;
- alert payload minimization;
- secrets scanning and redaction.

## Correlation example
```text
HTTP request
  request_id = R123
  correlation_id = C456
        |
        +--> domain transaction
        |      |
        |      +--> audit event
        |      +--> outbox event
        |
        +--> worker
               |
               +--> notification/document processor
                      |
                      +--> provider result
```

The same correlation chain must permit authorized investigation without requiring sensitive payloads in every log record.

## Observability vs Audit

**Audit:** authoritative security/business-action evidence.

**Logs:** operational diagnostics.

**Metrics:** aggregated measurements.

**Traces:** request execution relationships.

None may silently replace another.

Audit events must not be reconstructed solely from ordinary logs.

## Failure matrix
| Failure | Required behavior |
|---|---|
| Logging backend unavailable | core request behavior follows configured fail-safe logging policy; critical audit remains protected separately |
| Metrics backend unavailable | business operation continues; metrics may be lost according to telemetry policy |
| Trace backend unavailable | business operation continues |
| Database unavailable | readiness fails for DB-dependent operations; no fabricated success |
| Auth dependency unavailable | protected operations fail closed |
| Audit write unavailable | critical audited mutation follows P9.5 safe transaction policy |
| Outbox unavailable | critical transaction fails/rolls back if required outbox cannot be guaranteed |
| Storage unavailable | file operation fails safely; no false document success |
| WhatsApp unavailable | source domain transaction remains valid |
| AI unavailable | core operation remains available |
| Malformed telemetry input | reject/sanitize; never execute as code |

## Health/readiness semantics
Production status should distinguish:
```text
UP
DEGRADED
DOWN
DISABLED
```

Example:
- AI disabled intentionally → `AI_OPTIONAL = DISABLED`, overall core may remain `UP`.
- WhatsApp provider unavailable → notification component `DEGRADED`, domain core may remain `UP`.
- Database unavailable → `DATABASE = DOWN`, readiness for database-dependent service is `DOWN`.
- Audit integrity failure → security posture is critical and production gate may become blocked even if HTTP process is technically alive.
