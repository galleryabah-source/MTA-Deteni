# P10.12 — Database Rollback Plan

## Objective

Allow the proposed artifact grant schema to be removed safely if integration validation fails, without silently deleting unrelated application data.

## Before deployment

1. Confirm approved migration version and checksum.
2. Capture schema metadata and privilege/RLS policy inventory.
3. Confirm no production grant rows exist in the controlled integration environment.
4. Confirm backup/restore point is available and verified.
5. Record rollback owner and approval reference.

## Rollback order

1. Stop artifact-download grant writes through the application deployment gate.
2. Drain/stop workers that consume grant outbox events.
3. Confirm no active grant transaction is in progress.
4. Preserve audit and operational evidence.
5. Revert repository/application code only after durable database state is understood.
6. Remove grant-specific RLS policies and privileges introduced by the migration.
7. Drop grant-specific indexes.
8. Drop `public.artifact_download_grants` only if the approved rollback decision explicitly authorizes destructive rollback and the table contains no retained records required by policy.
9. Re-run schema/security verification.
10. Re-enable application traffic only after the rollback gate passes.

## Data-retention safeguard

A rollback must not silently destroy regulated or audit-required records. If grants have become part of an approved retention/audit chain, use a controlled archival procedure rather than destructive `DROP TABLE`.

## Partial-failure handling

If migration fails before commit, PostgreSQL migration transaction semantics must leave the schema unchanged where supported by the migration mechanism.

If deployment succeeds but application integration fails, keep the table isolated and deny access while the rollback decision is reviewed; do not improvise destructive SQL in production.

## Evidence

Rollback PASS requires observable before/after schema state, privilege state, RLS state, application availability state, and confirmation that audit/outbox integrity was preserved.

## Freeze rule

This document is a rollback plan only. No rollback operation is executed by P10.12 while `MIGRATION_FREEZE=TRUE`.
