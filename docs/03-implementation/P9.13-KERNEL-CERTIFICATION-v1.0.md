## 1. Objective

P9.13 certifies that the P9 platform kernel is actually enforceable in the runtime implementation. It does not certify the full MTA DETENI product or authorize production.

## 2. Certification principle

```text
CONTRACT
   ↓
IMPLEMENTATION
   ↓
EXECUTABLE TEST
   ↓
EVIDENCE
   ↓
INDEPENDENT REVIEW
   ↓
CERTIFICATION DECISION
```

Documentation alone cannot produce PASS.

A test that was not executed cannot produce PASS.

A green CI build cannot override a critical security/data-integrity failure.

## 3. Certification statuses

Each control is:

```text
PASS
FAIL
BLOCKED
NOT_RUN
PASS_WITH_NONCRITICAL_FINDINGS
```

Overall certification:

```text
CERTIFIED
CONDITIONALLY_CERTIFIED
BLOCKED
NOT_CERTIFIED
NOT_STARTED
```

`NOT_RUN` is never equivalent to PASS.

## 4. Certification gates

### K1 Runtime

Verify:
- application starts in controlled environment;
- health/live endpoint works;
- readiness correctly reflects critical dependencies;
- runtime configuration is validated;
- no production secrets are embedded.

### K2 Configuration

Verify:
- environment separation;
- required production settings are fail-closed;
- AI configuration remains optional when AI is disabled;
- secrets are not exposed to client code/logs;
- configuration changes are controlled.

### K3 Authentication

Verify:
- unauthenticated access is denied where required;
- session identity cannot be forged;
- disabled/revoked sessions cannot execute critical commands;
- logout/revocation works;
- authentication events are audited;
- enumeration resistance is preserved.

### K4 Authorization

Verify the complete authorization decision:

```text
Authentication
AND Role
AND Permission
AND Scope
AND Operational Assignment
AND Duty Status
AND Resource
AND Current State
AND Classification
AND Policy
```

Verify fail-closed behavior and Super Admin non-bypass.

### K5 Audit

Verify:
- mandatory critical mutations generate audit evidence;
- denied actions are auditable where required;
- actor/correlation/request context is preserved;
- history is immutable;
- hash-chain integrity detects tampering;
- writer/verifier canonical material is identical;
- audit query access is itself authorized.

### K6 Database Adapter

Verify:
- application accesses PostgreSQL through approved adapter/repository boundary;
- policy-sensitive mutations cannot bypass application/domain controls;
- test database is isolated;
- production database is rejected by test harness;
- database errors map safely to application errors.

### K7 Transaction + Idempotency

Verify:
- critical mutations are transactional;
- rollback leaves no prohibited partial state;
- duplicate request with same fingerprint replays safely;
- same key with different fingerprint conflicts;
- concurrent critical finalization produces at most one authoritative success;
- external providers do not become part of the authoritative transaction outcome.

### K8 Outbox

Verify:
- source mutation and outbox event are atomically recorded;
- worker claims are concurrency-safe;
- retry/dead-letter behavior is deterministic;
- stale leases recover;
- provider failure does not fabricate domain success/failure;
- duplicate delivery is controlled by idempotency.

### K9 Private Storage

Verify:
- protected objects are private;
- arbitrary storage keys are inaccessible;
- authorization/scope/classification are enforced;
- upload validation works;
- quarantine works;
- checksum integrity works;
- temporary download grants expire;
- signed URLs are not logged;
- immutable objects cannot be silently overwritten.

### K10 Observability

Verify:
- request/correlation IDs propagate;
- logs are structured;
- secrets and sensitive payloads are redacted;
- health/readiness semantics are correct;
- critical failure signals are observable;
- observability does not expose restricted information.

### K11 Test Harness

Verify:
- synthetic fixtures are deterministic and isolated;
- required personas exist;
- security tests execute;
- concurrency tests execute;
- failure injection executes;
- AI-OFF executes;
- evidence is generated;
- production database protection works.

### K12 CI Quality Gate

Verify:
- required CI stages execute;
- mandatory failures block;
- security failures block;
- AI-OFF failures block;
- migration freeze is enforced;
- secret detection exists;
- evidence is retained appropriately;
- protected branch requires mandatory checks once repository protection is configured.

## 7. Critical audit certification

The certification must intentionally tamper with a protected audit event in the isolated test environment and verify that the chain becomes invalid.

It must also prove that a valid append preserves chain integrity.

Audit evidence must be sufficient to trace:

```text
Actor
 → Request
 → Correlation
 → Authorization decision
 → Domain command
 → Transaction
 → State change
 → Audit event
 → Outbox event
```

where applicable.

## 8. Critical transaction certification

Failure injection must demonstrate:

```text
Domain mutation
+ audit
+ outbox
```

do not leave prohibited partial state when a mandatory transactional operation fails.

External work such as WhatsApp delivery or document processing may be asynchronous after a valid commit, provided its source event is durable and retryable.

## 13. Certification decision matrix

### CERTIFIED

Required:
- all K1–K12 critical controls PASS;
- mandatory kernel tests PASS;
- critical negative tests PASS;
- no P0/P1 blockers;
- audit integrity PASS;
- AI-OFF PASS;
- concurrency critical tests PASS;
- evidence complete.

### CONDITIONALLY_CERTIFIED

Only possible when:
- no P0/P1 blockers;
- no critical authorization/data/audit failure;
- remaining findings are non-critical;
- each finding has owner, remediation, due date, and risk acceptance where required.

Conditional certification does not mean production approval.

### BLOCKED / NOT CERTIFIED

Any critical requirement above fails or remains mandatory `NOT_RUN`.
