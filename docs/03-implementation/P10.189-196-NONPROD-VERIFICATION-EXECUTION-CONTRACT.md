# P10.189–P10.196 — Controlled Non-Production PostgreSQL Verification Contract

## Status

- Checkpoint: **P10.196**
- Classification: **BLOCKED_PENDING_GOVERNANCE**
- Migration Freeze: **TRUE**
- AI: **OFF**
- Data: **Synthetic only**
- Live PostgreSQL execution: **NOT AUTHORIZED**

## Purpose

Define the exact execution boundary for a future governed non-production PostgreSQL verification. This contract is executable only after an independent governance clearance satisfies the P10.181–P10.188 preflight. No live database operation is performed by creating or validating this document.

## P10.189 — Session initialization

The verification session must capture:

- immutable run ID;
- exact application commit SHA;
- target reference;
- database/schema identity without credentials;
- migration artifact hash;
- RLS artifact hash;
- test-suite hash;
- environment safety flags;
- operator and reviewer references.

## P10.190 — Connection safety

The execution client must reject:

- production target classification;
- missing explicit non-production approval;
- unexpected database identity;
- missing safety flags;
- credential material appearing in evidence.

Connection failure or identity mismatch aborts the run.

## P10.191 — Schema observation before mutation

Capture read-only observations before any mutation:

- schema objects relevant to the contract;
- table/column presence;
- constraint/index identity;
- RLS enabled/policy identity;
- migration state.

Unexpected drift is recorded and causes a controlled abort. No corrective migration is inferred automatically.

## P10.192 — Transaction verification

For each critical scenario:

```text
BEGIN
  authorization/context validation
  domain mutation
  audit event
  outbox event
COMMIT
```

Any failure must produce:

```text
ROLLBACK
```

Audit and outbox writes must use the same transaction boundary where the contract requires atomicity.

## P10.193 — Concurrency and state-transition verification

Verify at minimum:

- concurrent consume of the same ACTIVE grant;
- expiry at transition time;
- wrong actor;
- wrong scope;
- wrong object;
- concurrent revoke/consume;
- repeated request/idempotency;
- invalid state transition.

Expected behavior is fail-closed and observable through affected-row counts and final state.

## P10.194 — RLS and authorization verification

For each protected operation, evidence must demonstrate that access depends on the authenticated actor and applicable scope/policy, not merely on possession of a resource identifier.

Minimum negative cases:

- unauthenticated access;
- unauthorized role;
- wrong scope;
- direct object-ID manipulation;
- restricted-domain access;
- operational action without required duty.

## P10.195 — Provider isolation and evidence integrity

No WhatsApp, OCR, AI, notification, or other provider call may occur inside a critical database transaction. Provider work is eligible only after successful commit where the architecture permits it.

Evidence must contain no secret, token, password, production PII, or raw sensitive payload.

The final evidence manifest must be cryptographically bound and independently verifiable.

## P10.196 — Final classification

The governed run may end only as:

```text
PASS
FAIL
BLOCKED
```

`PASS` requires every mandatory scenario, integrity check, rollback condition, RLS check, and evidence check to pass.

`FAIL` means execution occurred under an approved scope but one or more required verification assertions failed.

`BLOCKED` means execution was not eligible or was safely aborted by a hard gate.

No `PASS` may be promoted to production authorization automatically.

## Abort conditions

Immediately classify the run BLOCKED/ABORTED on:

- production target detection;
- real detainee data detection;
- secret/credential leakage;
- unexpected schema mutation;
- authorization bypass;
- RLS failure;
- transaction boundary violation;
- audit/outbox atomicity failure;
- provider invocation inside transaction;
- rollback failure;
- evidence tampering;
- unexplained affected-row ambiguity.

## Evidence package

A completed governed run should produce:

1. preflight handoff;
2. environment and target identity;
3. read-only schema observation;
4. scenario matrix;
5. transaction outcomes;
6. RLS/authorization outcomes;
7. audit-chain evidence;
8. provider-isolation evidence;
9. rollback evidence;
10. artifact/evidence hashes;
11. final classification;
12. independent reviewer sign-off.

## Current boundary

This checkpoint remains a contract only. It does not perform live PostgreSQL execution, migration, production access, provider activation, or release. Those actions remain gated by explicit governance clearance and an approved non-production target.
