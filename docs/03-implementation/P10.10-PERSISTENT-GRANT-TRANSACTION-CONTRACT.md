# P10.10 — Persistent Grant / Revocation Transaction Boundary

## Status

IMPLEMENTED — persistence contract only; migration and real database integration remain blocked by the active Migration Freeze.

## Purpose

Define the database-backed contract required to replace the P10.8 in-memory grant lifecycle without weakening actor, scope, expiry, single-use, revocation, audit, or outbox invariants.

## Required persistence model

A future approved grant record must bind:

`grantId + documentId + artifactId + artifactSha256 + objectId + actorId + scopeId + issuedAt + expiresAt + status`

Mutable lifecycle states remain `ACTIVE`, `CONSUMED`, and `REVOKED`.

## Concurrency rule

Consumption must be one atomic database transition:

`ACTIVE + unexpired + actor + scope + object match → CONSUMED`

The repository adapter must require exactly one affected row. Zero rows means the grant is already consumed/revoked, expired, or authorization/binding does not match; the request fails closed. This eliminates a read-then-write race where two workers could both consume the same grant.

Revocation follows the same active-only atomic transition and requires actor and scope binding.

## Transaction rule

Grant creation, audit event and outbox event must be committed on the same PostgreSQL transaction connection. Provider/storage calls must occur only after the transaction commits and an outbox worker has durably claimed the event.

## Migration freeze

No DDL or migration is executed in P10.10. The repository currently remains migration-frozen and the Supabase public schema is empty. The contract is therefore implemented as a code/test boundary until schema approval and integration access are explicitly available.

## Evidence boundary

The included test suite verifies the persistence contract semantics and affected-row fail-closed rule. It does NOT certify PostgreSQL concurrency, isolation, RLS, persistent storage, or production deployment.

Certification remains `NOT CERTIFIED`.
