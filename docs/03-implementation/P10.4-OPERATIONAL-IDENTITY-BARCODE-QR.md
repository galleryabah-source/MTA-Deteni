# P10.4 — Operational Identity / Barcode-QR Boundary

**Status:** Executable foundation / NOT CERTIFIED  
**Data boundary:** Synthetic only  
**AI:** OFF  
**Migration freeze:** TRUE

## Objective

Provide a controlled operational identity boundary for barcode/QR scanning without allowing the scanned value itself to become an authorization credential.

## Contract

`Scanner Input → Normalize Opaque Identity → Resolve Identity → Authorization → Transaction → Audit → Outbox`

The scanner payload is untrusted input. It may identify an operational record, but identity resolution does not grant permission, scope, duty, classification access, or approval authority.

## Controls

- identity types are limited to BARCODE and QR;
- the operational token is opaque and must not embed direct detainee identifiers;
- malformed or unknown tokens fail closed;
- inactive resolved identities cannot proceed as an operational action;
- authorization is evaluated independently through the existing deny-by-default policy kernel;
- successful scans use the transactional command boundary;
- audit and outbox records are produced as critical side effects;
- idempotent replay does not duplicate those side effects;
- synthetic registry data is used for tests only.

## Security boundary

A QR/barcode is **not** an authorization token. Possession of a physical or copied code must never be sufficient to bypass RBAC/ABAC, duty, scope, classification, approval, or workflow controls.

No scan implementation may expose a detainee identifier in the encoded value as a design requirement. Production token generation, rotation, revocation, physical issuance, and database uniqueness remain future contract work.

## Test acceptance

P10.4 tests cover:

1. opaque identity normalization;
2. separation of identity resolution from authorization;
3. unknown-token fail-closed behavior;
4. malformed/tampered token rejection;
5. authorized transactional scan with audit/outbox;
6. unauthorized scan with zero critical side effects;
7. idempotent replay without duplicate side effects.

## Explicit production blockers

- PostgreSQL-backed identity registry and uniqueness constraints;
- atomic concurrent scan/revocation semantics;
- physical barcode/QR issuance and replacement policy;
- token rotation/revocation;
- runtime HTTP authentication/session integration;
- device/scanner trust model;
- complete audit-integrity evidence;
- UAT and operational SOP approval.

These are intentionally not implemented through schema migration at this checkpoint.
