# P9.6 — Authorization Matrix v1

## Purpose

Certify the canonical scope authorization boundary without provisioning production scope data.

## Required model

```text
Role + Permission + Scope + Duty + Resource + State + Policy
```

A role alone does not authorize a scoped operational resource.

## Matrix

| Case | Preconditions | Expected outcome |
|---|---|---|
| POSITIVE AUTHORIZATION | active profile, role OWNER/ADMIN, active membership to requested scope, resource belongs to requested scope | `AUTHORIZED` |
| `SCOPE_REQUIRED` | scoped operation has no requested scope | reject |
| `SCOPE_DENIED` | profile is inactive or role is outside OWNER/ADMIN for this controlled matrix | reject |
| `WRONG_SCOPE` | profile has membership to another scope, but not requested scope | reject |
| `INACTIVE_MEMBERSHIP` | matching profile/scope membership exists but is inactive | reject |
| `ROLE_DRIFT` | active membership expects OWNER/ADMIN but current profile role no longer matches | reject |
| `CROSS_SCOPE_ACCESS` | active membership authorizes requested scope, but resource belongs to another scope | reject |

## Controlled certification boundary

- Tests use synthetic identifiers only.
- No production `mta_scopes` row is inserted.
- No production `mta_profile_scopes` row is inserted.
- No RLS policy is bypassed.
- Scope identity remains explicit; it is never inferred from role.
- Production execution remains prohibited while `MIGRATION_FREEZE = TRUE`.

## Important distinction

The matrix is a policy oracle for deterministic certification. It is not a claim that production currently has a canonical scope. Production currently has no provisioned scope identity, so production scoped access must remain fail-closed rather than silently defaulting to an invented scope.

## Certification sequence

```text
positive authorization
        ↓
SCOPE_REQUIRED
        ↓
SCOPE_DENIED
        ↓
WRONG_SCOPE
        ↓
INACTIVE_MEMBERSHIP
        ↓
ROLE_DRIFT
        ↓
CROSS_SCOPE_ACCESS
        ↓
P9.6 FINAL CERTIFICATION
```
