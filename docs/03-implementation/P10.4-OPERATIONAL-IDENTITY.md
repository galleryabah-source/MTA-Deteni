# MTA DETENI — P10.4 Operational Identity / Barcode-QR Boundary

**Status:** IMPLEMENTED / EXECUTION EVIDENCE PENDING

## Objective

Provide a privacy-preserving operational identity boundary suitable for barcode/QR presentation without embedding detainee personally identifiable information in the code value.

## Security contract

- QR/barcode payload is an opaque, signed token; it is not a database identifier intended for public disclosure.
- No name, NIK, passport number, date of birth, address, telephone number, health information, or other direct PII is embedded in the token.
- Token integrity uses HMAC-SHA-256.
- Signing secrets are fail-closed: production code must supply a secret of at least 32 characters.
- Token purpose is cryptographically bound at verification time to prevent cross-context reuse.
- Tokens have a bounded expiry and reject timestamps materially in the future.
- Revocation is supported through a nonce-based revocation callback; persistent revocation storage belongs to the approved domain schema and remains outside the migration-freeze boundary.
- Constant-time signature comparison is used for verification.
- The identity layer does not grant authorization. Existing RBAC/ABAC, scope, duty, classification, lifecycle, and SoD checks remain mandatory.
- The identity token is an operational presentation mechanism, not proof that an action is authorized.

## Explicit non-goals

- No schema migration is introduced.
- No real detainee data is introduced.
- No secret is committed to the repository.
- No production storage or external QR provider is invoked.
- No authorization decision is made solely from the token.

## Test coverage

`test/p10.4-operational-identity.test.mjs` covers:

1. opaque token issuance without PII;
2. signature tampering rejection;
3. purpose binding;
4. expiry enforcement;
5. revocation;
6. weak-secret fail-closed behavior.

## Integration gate

P10.4 is not certified until CI evidence is independently observable and the token boundary is exercised through the runtime/domain integration path. Persistent revocation, database-backed identity mapping, scanner/device policy, and production key management remain downstream integration concerns.
