# P10.12 — RLS Policy Contract

## Status

CONTRACT ONLY — no policy has been deployed.

## Security objective

`artifact_download_grants` is security-sensitive authorization state. RLS must prevent anonymous/public access and enforce actor/scope isolation without becoming the application's authorization decision point.

## Required layers

1. Application Authorization Control Plane evaluates authentication, permission, scope, assignment/duty, classification, state and policy.
2. Repository SQL uses actor/scope/object predicates for lifecycle transitions.
3. PostgreSQL RLS prevents unauthorized row visibility/manipulation if a role reaches the table.
4. Explicit Postgres grants remain separate from RLS.
5. Provider/storage access is outside the database transaction and remains bound to the committed outbox event.

## Deny-by-default

Before production integration:

- `anon` has no table privileges.
- `public` has no table privileges.
- `authenticated` has no table privileges unless an explicitly approved policy and privilege model requires it.
- server-side integration uses an approved privileged role and still performs application authorization before repository access.
- no policy uses a client-controlled field as proof of authorization.

## Identity mapping requirement

The final policy must define an authoritative mapping between the authenticated principal and `actor_id`, and an authoritative scope context for `scope_id`. The implementation must not infer authorization from arbitrary request parameters.

A candidate Supabase implementation may use JWT identity plus a server-established scope claim, but this remains a design option until the MTA DETENI identity contract is approved.

## Lifecycle restrictions

RLS must not weaken these repository invariants:

- consume: `ACTIVE AND expires_at > now AND actor_id = actor AND scope_id = scope AND object_id = object`;
- revoke: `ACTIVE AND actor_id = actor AND scope_id = scope`;
- exactly one affected row is required;
- zero affected rows fail closed.

## Sensitive operation policy

Creation, consumption and revocation are not ordinary CRUD. The preferred production architecture is a server-side repository using an approved privileged database role, with application authorization and audit/outbox transaction controls surrounding the operation. Direct browser writes to grant rows are prohibited.

## Verification matrix

| Test | Expected |
|---|---|
| anonymous SELECT | DENY |
| anonymous INSERT | DENY |
| authenticated direct SELECT without approved policy | DENY |
| authenticated direct INSERT without approved policy | DENY |
| wrong actor | DENY / zero affected rows |
| wrong scope | DENY / zero affected rows |
| wrong object | DENY / zero affected rows |
| expired grant consume | zero affected rows |
| consumed grant replay | zero affected rows |
| revoked grant replay | zero affected rows |
| authorized server repository | ALLOW subject to ACP |

## Supabase alignment

Supabase documents that grants and RLS are separate layers: explicit grants determine whether a role can access a table, while RLS determines which rows are accessible. The current platform rollout also removes automatic public-schema Data API exposure for new tables, but the project must still explicitly deny public/anonymous access in the migration contract.

## Gate

No RLS policy is considered PASS until executed against the deployed schema with role-specific tests and observable evidence.
