# P10.937–P10.968 — Synthetic Execution Evidence Gate

## Purpose

Advance beyond the P10.936 contract milestone without claiming execution that has not been observed. This gate separates **contract readiness** from **execution evidence** and keeps the project pre-authorisation.

## Checkpoint groups

| Checkpoints | Focus | Evidence boundary |
|---|---|---|
| P10.937–944 | release-candidate identity, completeness and fail-closed validation | SYNTHETIC |
| P10.945–952 | execution-evidence shape for typecheck/test/regression commands | SYNTHETIC |
| P10.953–960 | NOT_RUN, non-zero exit and missing-evidence rejection | SYNTHETIC |
| P10.961–968 | packet-level synthetic-only boundary and pre-authorisation discipline | SYNTHETIC |

## Evidence contract

An execution evidence record must identify the checkpoint, control, command, target, status, exit code and output digest. A synthetic packet is READY only when every control is PASS, every command/evidence identity is non-blank, every exit code is zero, and the target is SYNTHETIC.

The contract does **not** convert a declared synthetic record into proof that a command actually ran. Real execution evidence must be produced by an observable local or CI execution environment and recorded separately from contract fixtures.

## Required execution sequence

1. `npm install --ignore-scripts --no-audit --no-fund`
2. `npm run typecheck`
3. `npm test`
4. `npm run test:unit`
5. inspect the corresponding GitHub Actions run and job telemetry;
6. record PASS/FAIL/NOT_RUN based only on observable results;
7. resolve failures before a later non-production request.

## Safety boundary

- Migration Freeze remains TRUE.
- AI remains OFF.
- Production access remains NOT AUTHORIZED.
- No live PostgreSQL execution is implied.
- No schema migration is implied.
- Repository fixtures remain synthetic only.
- No real detainee PII, credentials, health records or operational exports may be introduced.

## Exit condition

P10.968 is a **contract-level evidence gate**. It becomes execution-certified only after trustworthy runtime/CI telemetry is observed. Until then, project status must explicitly distinguish `CONTRACT READY` from `EXECUTION VERIFIED`.
