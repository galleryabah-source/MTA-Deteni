# P10.13 — Identity and Scope RLS Finalization Contract

## Status

PREPARED — governance gate only. No RLS policy is deployed and no migration is executed.

## Objective

Define the authoritative identity-to-actor and scope context required before authenticated PostgreSQL access can be enabled for `artifact_download_grants`.

## Authoritative mapping

1. Authentication establishes the authenticated principal.
2. The server resolves that principal to an opaque `actor_id` from an authoritative identity source.
3. The server establishes `scope_id` from an authoritative assignment/scope source; client-supplied scope is never trusted as authorization proof.
4. The Application Authorization Control Plane (ACP) evaluates permission, scope, assignment/duty, classification, state and policy before repository access.
5. PostgreSQL RLS is defense-in-depth and must not broaden authorization granted by ACP.

## Required production contract

The implementation must document and verify:

- principal identifier and its trusted issuer;
- actor mapping source and uniqueness guarantee;
- active/inactive actor semantics;
- authoritative scope membership source;
- scope lifecycle and revocation behavior;
- server-side propagation of actor/scope context to PostgreSQL;
- behavior when identity or scope mapping is missing, stale, ambiguous or revoked.

Any missing, ambiguous or conflicting mapping MUST fail closed.

## Candidate Supabase pattern

A server-side Supabase integration may derive the authenticated principal from the verified JWT and establish scope context on the trusted server side. This is a candidate pattern, not an approved production policy. No client-controlled JWT field or request parameter may independently authorize access to a grant row.

## RLS policy shape

When approved, policies must enforce the same actor/scope boundary used by the repository:

- visibility only for the authoritative actor/scope context;
- no direct browser INSERT/UPDATE/DELETE;
- lifecycle transitions remain atomic repository operations;
- zero affected rows remain a fail-closed result;
- privileged server access remains wrapped by ACP authorization and audit/outbox transaction controls.

## Verification matrix

| Scenario | Required result |
|---|---|
| missing principal | DENY |
| unmapped principal | DENY |
| inactive actor | DENY |
| missing scope | DENY |
| revoked scope membership | DENY |
| client-supplied actor mismatch | DENY |
| client-supplied scope mismatch | DENY |
| wrong actor with valid scope | DENY / zero rows |
| wrong scope with valid actor | DENY / zero rows |
| valid actor + valid scope + ACP allow | ALLOW only through approved server path |

## Approval gate

No authenticated RLS policy is considered approved until the identity and scope sources, mapping semantics, server propagation mechanism, role privileges and role-specific tests are reviewed and recorded as evidence.

Migration Freeze remains TRUE. This document does not authorize DDL, policy deployment or production database access.
