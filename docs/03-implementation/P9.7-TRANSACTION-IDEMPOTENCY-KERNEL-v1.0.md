## Objective
Provide a single, auditable transaction and idempotency boundary for critical commands. The kernel prevents partial domain commits, duplicate command effects, unsafe retries, and concurrent double-finalization.

## Non-negotiable invariants
1. Critical domain commands execute inside an explicit transaction boundary.
2. A successful command has one authoritative commit outcome.
3. Retry of the same idempotency key cannot create a second business effect.
4. An idempotency key cannot be reused for a materially different request.
5. Concurrent finalization yields at most one successful state transition.
6. Audit evidence for mandatory critical mutations is part of the safe transaction policy.
7. Outbound notifications are not used as the transaction's source of truth; they will be emitted through the later outbox layer.
8. AI is outside the critical transaction path and cannot commit canonical state.
9. Generic status updates are prohibited for protected state machines.
10. Transaction failure must not leave a half-completed leave/handover/movement/escort chain.

## Transaction API contract
```ts
export type TransactionContext = {
  transactionId: string;
  correlationId: string;
};

export interface TransactionManager {
  run<T>(work: (tx: TransactionContext) => Promise<T>): Promise<T>;
}
```

The concrete adapter must bind the context to one database transaction and must guarantee commit/rollback semantics.

## Idempotency contract
```ts
export type IdempotencyRequest = {
  key: string;
  commandName: string;
  actorId: string;
  requestFingerprint: string;
  correlationId: string;
};

export type IdempotencyResult<T> =
  | { state: "NEW"; value?: T }
  | { state: "REPLAY"; value: T }
  | { state: "CONFLICT"; reasonCode: string };
```

Recommended persisted material:
- idempotency key
- command name
- actor
- request fingerprint
- status: IN_PROGRESS / SUCCEEDED / FAILED
- response snapshot or safe replay reference
- correlation ID
- timestamps
- expiry/retention according to policy

The exact database table is NOT created in this phase; schema remains frozen until database contract audit is approved.

## Command processing
```text
REQUEST
  ↓
AUTHENTICATION
  ↓
AUTHORIZATION
  ↓
INPUT VALIDATION
  ↓
IDEMPOTENCY CHECK
  ↓
BEGIN TRANSACTION
  ↓
LOCK / CONCURRENCY CONTROL
  ↓
DOMAIN VALIDATION
  ↓
DOMAIN MUTATION
  ↓
MANDATORY AUDIT
  ↓

  ↓
COMMIT
  ↓

```

## Retry rules
- Same key + same fingerprint + completed result = deterministic replay.
- Same key + different fingerprint = `IDEMPOTENCY_CONFLICT`.
- Same key + IN_PROGRESS = do not execute a second command; return/retry according to policy.
- Failed transaction must not be reported as successful.
- Network timeout after commit must be recoverable through idempotent replay.

## Concurrency
Critical commands must use database-supported concurrency control. For final leave receipt, the protected resource is the leave request and its current state.

Example:
```text
Officer A ─┐
           ├─ RECEIVE
Officer B ─┘

Expected:
A = SUCCESS
B = ALREADY_RECEIVED / CONCURRENT_MODIFICATION
```

Never:
```text
A = SUCCESS
B = SUCCESS
```

## Duty Officer finalization invariant
A transaction that completes temporary leave must validate, in one protected command boundary:
- authenticated actor;
- `leave.receive` permission;
- PETUGAS_JAGA operational assignment;
- active duty;
- correct scope;
- valid Seksi Keamanan & Ketertiban handover;
- valid leave state `HANDED_OVER_TO_SECURITY`;
- detainee identity;
- valid QR or authorized manual confirmation;
- no previous receipt/completion.

The transaction may then create the handover evidence, movement return, leave completion, linked escort update, overdue resolution, reconciliation event, notification outbox event, and audit evidence according to domain policy.

## Atomicity policy
Critical cross-domain finalization is treated as one atomic business transaction where the same database boundary permits it. If a required mutation cannot be committed, the transaction rolls back. External provider delivery is deliberately outside the transaction and is handled by outbox processing.

## Failure matrix
| Failure | Required behavior |
|---|---|
| Validation failure | No mutation |
| Authorization failure | No mutation; audit denial |
| Idempotency conflict | No mutation |
| Concurrent state change | Rollback; return conflict/state error |
| Domain mutation failure | Rollback |
| Mandatory audit failure | Safe failure/rollback according to critical audit policy |
| Outbox insert failure | Rollback critical transaction |
| WhatsApp provider failure | Domain transaction remains valid; outbox retries later |
| AI unavailable | Core transaction remains fully operational |
| Response/network timeout after commit | Client retry safely replays committed result |

## Prohibited patterns
- Generic `PUT` that accepts client-supplied status.
- Client-generated authoritative timestamps for business events.
- Client-generated final state.
- Notification provider as transaction coordinator.
- WhatsApp webhook as state authority.
- AI response as commit authority.
- Read-then-write without concurrency protection for critical state.
- Swallowing transaction errors.
- Retrying a non-idempotent command blindly.
