# P10.12 — PostgreSQL Concurrency Test Plan

## Objective

Produce independent evidence that artifact-download grants are single-use under concurrent PostgreSQL transactions and that the repository cannot double-consume an active grant.

## Preconditions

- approved migration deployed to an isolated test database;
- synthetic document/artifact/grant fixtures only;
- two or more independent PostgreSQL connections;
- identical grant available in `ACTIVE` state;
- no provider/network dependency in the critical transaction.

## Test C1 — Concurrent consume

1. Begin transaction A and transaction B on separate connections.
2. Submit the same grant ID with identical actor, scope, object and current time.
3. Execute the conditional consume UPDATE concurrently.
4. Commit both transactions.
5. Assert exactly one transaction reports `rowCount = 1`.
6. Assert the other reports `rowCount = 0` and fails closed.
7. Assert final state is `CONSUMED` with exactly one `consumed_at`.

## Test C2 — Expiry race

Run consume immediately before and immediately after `expires_at` using independent connections. Only the unexpired attempt may succeed.

## Test C3 — Wrong binding race

Concurrent attempts with wrong actor, scope and object must all produce zero affected rows and must not alter state.

## Test C4 — Revocation race

Race revoke against consume. The evidence must demonstrate that no execution path results in two successful terminal transitions. Exactly one conditional transition may win; the loser fails closed.

## Test C5 — Rollback

Inject an audit or outbox failure after grant insert. Assert the grant insert is rolled back and no durable outbox event remains.

## Test C6 — Provider isolation

Verify the provider is not invoked before transaction commit. Provider work may begin only after a durable outbox claim.

## Evidence required

For each test record:

- database engine/version;
- transaction isolation level;
- connection/session identifiers;
- SQL operation fingerprint;
- start/commit timestamps;
- row counts;
- final row state;
- audit event IDs;
- outbox event IDs/status;
- provider invocation timestamp where applicable.

## Pass criteria

`PASS` requires independently observable database evidence. Synthetic/in-memory tests do not substitute for PostgreSQL concurrency evidence.
