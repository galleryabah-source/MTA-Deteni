# P9.6 — Canonical Scope Identity Source-of-Truth Audit

## Finding

No authoritative repository or production schema source currently specifies a concrete canonical `mta_scopes.code` or `mta_scopes.name`.

## Sources checked

### Production migration history

The applied migration `20260922075730_mta_canonical_scope_and_qr_registry` defines:

- `mta_scopes.id`
- `mta_scopes.code` — unique
- `mta_scopes.name`
- `mta_scopes.active`
- timestamps

It states that the design uses **one explicit operational scope per detainee** and that users gain access through `mta_profile_scopes`.

It does **not** insert a scope row and does not prescribe a concrete code/name.

### Repository migrations

The same historical migration has now been restored to repository provenance. No seed scope row is present.

### Authorization documentation

The authorization contracts define scope conceptually as a unit/site/context authorization dimension, but no concrete production scope identifier is prescribed.

### Current production data

Current production contains:

- zero rows in `mta_scopes`;
- zero `mta_profile_scopes` memberships for the existing OWNER and ADMIN profiles.

## Decision

The system must **not invent** a canonical scope identity.

The unresolved contract is therefore:

```text
CANONICAL_SCOPE_CODE = UNRESOLVED
CANONICAL_SCOPE_NAME = UNRESOLVED
```

This is a genuine governance/data-model input, not an implementation defect that should be hidden by a default.

## Consequence

P9.6 can safely proceed with:

- schema reconciliation;
- provisioning manifest validation;
- transactional non-production provisioning mechanics;
- positive/negative authorization tests.

P9.6 must not yet:

- seed production scope data;
- assign production OWNER/ADMIN profiles;
- assume a global single-scope invariant;
- infer scope identity from role;
- bypass `SCOPE_REQUIRED`.

A concrete scope code/name may be introduced only from an explicit authoritative source (approved facility/site identity or equivalent governed configuration).
