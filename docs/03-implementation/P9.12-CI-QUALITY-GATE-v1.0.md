## Status
CONTRACT COMPLETE / IMPLEMENTATION NOT VERIFIED / MIGRATION FREEZE = TRUE / PRODUCTION = NO-GO

## 1. Objective

P9.12 defines the mandatory continuous-integration quality gate for MTA DETENI. CI is a merge/release control mechanism: a change must not be treated as safe merely because it builds.

The gate verifies, in dependency order, repository integrity, dependency installation, static checks, type safety, automated tests, security tests, concurrency behavior, failure handling, AI independence, build integrity, and certification evidence readiness.

A CI result is evidence for a specific commit, environment, configuration, and test scope. It is not by itself production certification.

## 3. Mandatory CI stages

### CI-01 Repository integrity

Verify:
- repository contains no prohibited real operational data;
- no credentials/secrets/tokens are committed;
- no generated sensitive artifacts are committed;
- expected project files are structurally valid;
- migration freeze has not been bypassed;
- test fixtures remain synthetic.

### CI-02 Dependency integrity

Verify:
- lockfile is present and consistent;
- dependency installation is reproducible;
- dependency scripts do not unexpectedly mutate production resources;
- dependency changes are reviewable;
- known critical dependency/security findings block according to policy.

### CI-03 Static quality

Verify lint/static analysis and project-specific policy checks.

### CI-04 Type safety

TypeScript strict checking must pass for the implementation.

Security/domain code must not silently introduce `any` without an explicit documented exception.

### CI-05 Unit tests

Execute deterministic unit suites covering domain and kernel logic.

### CI-06 Integration tests

Execute controlled tests against isolated test infrastructure.

Production databases are prohibited.

### CI-07 Security tests

At minimum execute applicable tests for:
- authentication bypass;
- RBAC/ABAC bypass;
- scope bypass;
- IDOR/BOLA;
- mass assignment;
- CSRF/CORS;
- rate limiting;
- path traversal;
- upload abuse;
- webhook forgery;
- classification bypass;
- uncontrolled export;
- Super Admin operational-authority bypass;
- secret leakage.

### CI-08 Concurrency tests

Execute protected race-condition tests, especially:
- duplicate Duty Officer receipt;
- duplicate leave completion;
- concurrent idempotency requests;
- duplicate outbox claim;
- concurrent RBAC mutation;
- duplicate document generation where protected.

Critical finalization must produce at most one authoritative success.

### CI-09 Failure injection

Execute deterministic failure scenarios for critical infrastructure/provider boundaries:
- database failure;
- transaction rollback;
- audit failure;
- outbox failure;
- worker crash/stale lease;
- storage failure;
- checksum failure;
- notification timeout/permanent failure;
- malformed webhook;
- document generation failure;
- AI timeout/unavailable/malformed response.

### CI-10 AI-OFF

CI must explicitly execute with:

```text
AI_ENABLED=false
AI_API_KEY absent
external AI connectivity blocked
```

Core functions must remain testable without AI.

A test cannot claim AI-OFF if it silently calls a live provider.

### CI-11 Audit integrity

Where the audit engine exists, CI must verify:
- canonical event material;
- deterministic serialization/versioning;
- hash-chain continuity;
- tamper detection;
- writer/verifier material equivalence;
- required audit on protected mutations.

### CI-12 Build/package

The application must build successfully under the declared supported runtime configuration.

A successful build does not override failed security or certification gates.

## 4. Quality status model

Every stage uses:

```text
PASS
FAIL
BLOCKED
NOT_RUN
```

Rules:
- `NOT_RUN` is never PASS;
- `SKIPPED` is never PASS for a mandatory gate;
- infrastructure failure is not silently converted into success;
- flaky tests remain visible;
- a manually overridden failure requires explicit authorized evidence and does not erase the original failure.

## 5. Hard-block policy

The CI gate must block merge/release for:

- P0 security finding;
- P1 security finding unless an explicitly approved certification policy says otherwise;
- authentication bypass;
- authorization/RBAC bypass;
- scope/ABAC bypass;
- IDOR/BOLA;
- sensitive-data exposure;
- audit integrity failure;
- source-of-truth violation;
- transaction atomicity failure;
- idempotency/concurrency failure on critical commands;
- unauthorized Duty Officer finalization;
- uncontrolled export;
- secret exposure;
- production database access from tests;
- unauthorized migration;
- AI dependency in a core path;
- AI-OFF failure for a core function;
- build failure;
- mandatory test suite not executed.

## 6. Critical leave/handover gate

The pipeline must preserve the business rule:

> Final temporary-leave completion belongs to an authorized active Petugas Jaga/Duty Officer after valid handover from Seksi Keamanan dan Ketertiban.

CI must prove at minimum:

```text
non-duty user                    → DENY
permission but wrong scope      → DENY
inactive duty                   → DENY
missing security handover       → DENY
invalid QR                      → DENY
already received                → DENY / REPLAY by command semantics
concurrent receipt              → max 1 success
valid active Duty Officer       → ALLOW
```

QR scanning alone must never be treated as final completion.

## 7. Migration freeze enforcement

Until the database contract audit and migration governance gate are formally released:

```text
MIGRATION_FREEZE = TRUE
```

CI should detect and block unauthorized schema/migration activity, including:
- new migration files without an approved change reference;
- migration execution in ordinary test/CI paths against production;
- destructive schema operations outside approved migration tests;
- schema changes that bypass the contract process.

P9.12 does not authorize any production migration.

## 8. Test environment safety

CI test jobs must use isolated resources.

Required safeguards:
- explicit `TEST` environment marker;
- production connection rejection;
- synthetic fixture version;
- disposable/resettable test database where integration tests require PostgreSQL;
- isolated object storage namespace/bucket;
- fake notification provider;
- fake AI provider;
- no production credentials;
- no real detainee data.

If environment identity is ambiguous, the test must fail closed.

## 9. Secret and sensitive-data gate

CI must inspect tracked files and relevant generated artifacts for:
- passwords;
- API keys;
- session secrets;
- provider tokens;
- private keys;
- WhatsApp credentials;
- database credentials;
- production URLs containing credentials;
- real detainee identifiers or documents.

Detection must distinguish approved placeholders/test fixtures from secrets.

False positives may be reviewed, but a secret finding cannot be silently ignored.

## 11. Artifact retention

CI artifacts are retained according to policy.

Examples:
- test reports;
- coverage reports;
- security reports;
- failure-injection summaries;
- AI-OFF results;
- audit-integrity verification;
- build metadata.

Sensitive artifacts must not be published as public workflow artifacts.

## 12. Branch and merge policy

The protected/default branch must require the mandatory CI checks once runtime implementation exists.

Recommended required checks:

```text
repository-integrity
static-quality
typecheck
unit
integration
security
concurrency
failure-injection
ai-off
audit-integrity
build
```

No direct merge should bypass required checks except through a formally authorized emergency/change-control procedure, which must itself be auditable.

## 13. Pull-request policy

Every material implementation PR should identify:
- affected domains;
- contract IDs affected;
- security impact;
- data impact;
- migration impact;
- test IDs added/changed;
- AI impact;
- storage/notification impact;
- rollback considerations.

A PR that changes authorization-sensitive code without corresponding security tests should be blocked by policy.

## 14. Coverage and mutation policy

Coverage is informative, not sufficient.

For critical domain/security code, contract-specific tests are mandatory even when line coverage is high.

Mutation testing may be introduced for authorization/state-machine code where practical. A mutation that removes a security guard should be detected by the test suite.

## 15. Flaky test policy

CI must not use retries to conceal deterministic failures.

If infrastructure retry is permitted:
- original failure is recorded;
- retry count is recorded;
- instability is visible;
- repeated flakiness becomes a maintenance finding.

Security and concurrency failures must not be silently retried into apparent PASS.

## 16. CI performance policy

Stages should be ordered so inexpensive deterministic checks fail early while expensive suites run after prerequisites pass.

Parallel execution is permitted only where test isolation is proven.

Concurrency tests intentionally remain concurrency-sensitive and must not be serialized merely to make CI green.

## 17. Failure handling

A CI failure must provide:

```text
FAILED STAGE
TEST ID
COMMIT SHA
CORRELATION/EVIDENCE REF
ERROR CLASS
REPRODUCTION INFORMATION
```

Sensitive request/response payloads must be redacted.

## 19. Acceptance criteria

P9.12 is implementation-complete only when:

1. a CI workflow is executable;
2. mandatory stages are represented;
3. production database access is technically rejected in test jobs;
4. synthetic fixtures are enforced;
5. mandatory security checks execute;
6. concurrency checks execute;
7. failure injection executes;
8. AI-OFF executes with external AI blocked;
9. audit-integrity checks execute when the audit engine exists;
10. migration-freeze enforcement exists;
11. secret detection exists;
12. machine-readable evidence is generated;
13. mandatory checks are required for merge on the protected branch;
14. `NOT_RUN` cannot become PASS;
15. failures remain traceable to commit and test evidence.
