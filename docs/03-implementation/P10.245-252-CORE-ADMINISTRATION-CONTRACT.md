# P10.245–P10.252 — Core Administration Contract

## Purpose

Define the first operational domain contract for MTA DETENI Digital. This contract consumes the existing authorization, transaction, audit, provenance, and restricted-domain boundaries; it does not create alternate security paths.

## P10.245 — Detainee identity

The master record represents administrative identity and operational status only. Required concepts: stable detainee identifier, administrative identity fields, status, lifecycle timestamps, classification, verification state, provenance reference, and created/updated metadata.

## P10.246 — Status history

Material status changes are append-only events. Current status is a projection of accepted history, not an invitation to overwrite historical facts.

## P10.247 — Provenance

Every material identity/document fact must identify its source class, capture timestamp, verification state, and actor/process responsible for acceptance. Imported or AI/OCR-derived values remain draft until validated.

## P10.248 — Completeness and verification

The domain distinguishes missing, present-unverified, verified, rejected, and superseded information. Validation must be explicit and auditable.

## P10.249 — Classification boundary

Ordinary RAP/KAMTIB operational records may not expose restricted PERKES/health fields. Restricted health information remains isolated by domain and authorization scope.

## P10.250 — CRUD/action contract

Create, amend, verify, supersede, view, export, and archive are separate actions. Authorization is evaluated server-side using actor, role/permission, domain, object scope, and context. UI visibility never constitutes authorization.

## P10.251 — Audit/idempotency/error behavior

Material mutations require transactionally coupled audit/outbox evidence. Replayed requests must not create duplicate material records. Errors are classified into validation, authorization, conflict, state, integrity, and system categories without leaking restricted payloads.

## P10.252 — Acceptance

Synthetic fixtures must demonstrate: authorized creation; unauthorized denial; field/domain isolation; status history preservation; provenance capture; verification workflow; idempotent replay; audit evidence; and fail-closed behavior on ambiguous authorization.

## Safety invariant

> Core Administration stores the administrative truth of the detainee lifecycle while preserving history, provenance, least privilege, and restricted-domain separation.

## Dependency

`Security/transaction kernel → Core Administration → Placement`.
