## Status
CONTRACT COMPLETE / IMPLEMENTATION NOT VERIFIED / MIGRATION FREEZE = TRUE / PRODUCTION = NO-GO

## 1. Objective

P9.11 establishes the executable testing foundation for the MTA DETENI runtime. The harness must prove that the security and reliability contracts defined in P9.1–P9.10 are enforceable in code, not merely documented.

The test harness is a control mechanism. A green test result is evidence for a specific test scope and commit; it is not a substitute for production certification.

## 2. Test architecture

```text
                 TEST HARNESS
                      |
        +-------------+-------------+
        |             |             |
      UNIT       INTEGRATION     SECURITY
        |             |             |
        +-------------+-------------+
                      |

                      |

                      |
                   E2E

```

Tests must use synthetic fixtures unless a separately approved certification environment explicitly permits controlled operational data.

## 3. Test layers

### Unit

Verify pure/domain/application logic without requiring external providers.

Examples:
- authorization decision matrix;
- state-transition guards;
- request validation;
- error mapping;
- checksum/canonicalization helpers;
- retry classification;
- storage-key validation;
- notification recipient policy;
- document variable validation.

### Integration

Verify interactions between application services and controlled infrastructure adapters.

Examples:
- database repository;
- transaction manager;
- idempotency store;
- audit writer;
- outbox;
- private storage adapter;
- authentication/session adapter.

### Security

Tests must attempt prohibited behavior, not only valid behavior.

Required classes:
- authentication bypass;
- authorization bypass;
- scope/ABAC bypass;
- IDOR/BOLA;
- mass assignment;
- CSRF/CORS;
- rate limiting;
- path traversal;
- file upload abuse;
- secret leakage;
- webhook forgery;
- uncontrolled export;
- classification bypass;
- Super Admin operational-authority bypass.

### Concurrency

Critical commands must be exercised concurrently.

Minimum targets:
- duplicate leave completion;
- duplicate Duty Officer receipt;
- concurrent RBAC change;
- duplicate outbox claim;
- duplicate document generation;
- concurrent export/download grant;
- concurrent placement mutation where relevant.

Expected result for protected finalization: at most one authoritative success.

### Failure injection

The harness must deliberately simulate infrastructure and provider failures.

Examples:
- database unavailable;
- transaction rollback;
- audit write failure;
- outbox insertion failure;
- worker crash;
- stale lease;
- storage unavailable;
- checksum mismatch;
- notification provider timeout;
- notification provider permanent failure;
- malformed webhook;
- document generation failure;
- AI timeout;
- AI malformed output;
- AI unavailable.

## 4. Synthetic fixture policy

Fixtures must be clearly synthetic and must not resemble unnecessary real operational records.

Fixture requirements:
- deterministic IDs where useful;
- deterministic timestamps where useful;
- synthetic names/nationalities;
- no production credentials;
- no real detainee documents;
- no production WhatsApp numbers/tokens;
- no live AI provider dependency;
- isolated test database/environment;
- cleanup or disposable database strategy;
- fixture versioning.

Fixtures must model important relationships, including:

```text
Detainee
  ↓
Placement
  ↓
Leave
  ↓
Approval
  ↓
Escort
  ↓
Movement
  ↓
Security/Kamtib Handover
  ↓
Duty Officer Receipt
  ↓
Leave Completion
```

## 5. Test identity model

Tests must explicitly distinguish:

```text
USER
ROLE
PERMISSION
SCOPE
OPERATIONAL ASSIGNMENT
DUTY STATUS
RESOURCE STATE
POLICY VERSION
```

Do not create a single privileged fixture and use it for every test. That would hide authorization defects.

Required personas include at minimum:
- unauthenticated actor;
- authenticated user without permission;
- authenticated user with permission but wrong scope;
- authorized operational user without active duty;
- active Petugas Jaga with correct scope;
- KAMTIB/security actor;
- reviewer;
- approver;
- auditor;
- Super Admin attempting an operational bypass.

## 6. Test database isolation

Tests must never silently execute against a production database.

Required safeguards:
- explicit test environment marker;
- isolated connection/configuration;
- destructive-test protection;
- production connection rejection;
- fixture namespace or disposable database strategy;
- transaction cleanup where appropriate;
- deterministic seed/reset strategy.

A test command must fail closed if the environment is ambiguous or identifies itself as production.

## 13. Negative-path philosophy

For security-critical functionality, negative tests are first-class acceptance criteria.

Examples:
- client supplies protected status field → reject;
- client changes actor identity → reject;
- Super Admin tries operational completion without duty authority → reject;
- direct API call bypassing UI → reject;
- wrong scope → reject;
- classification mismatch → reject;
- duplicate idempotency key with different fingerprint → conflict;
- second concurrent finalization → reject/replay according to command semantics;
- audit failure on mandatory audited mutation → safe failure;
- outbox failure on mandatory event → safe rollback;
- AI failure → core operation remains available.

## 14. AI-OFF test mode

The harness must support an explicit:

```text
AI_ENABLED=false
```

mode and must be able to remove or block external AI connectivity.

Mandatory AI-OFF assertions include:
- application starts;
- authentication works;
- authorization works;
- detainee/placement operations work;
- movement works;
- leave workflow works;
- Duty Officer receipt works;
- escort workflow works;
- document generation path works where it does not require AI;
- follow-up works;
- emergency works;
- notification event/outbox works;
- reconciliation works;
- reporting works;
- controlled export works;
- audit works.

No test may quietly call a real AI provider while claiming AI-OFF.

## 15. Provider isolation

External providers must be replaced by deterministic test doubles/mocks/adapters during ordinary automated tests.

Examples:
- WhatsApp provider fake;
- object storage fake or isolated bucket;
- AI provider fake;
- email provider fake if later added;
- external identity provider fake where practical.

Provider test doubles must support failure modes, not only success.

## 16. Audit verification in tests

For every critical mutation, tests should assert the presence and semantics of the required audit evidence.

Where hash chaining is implemented, tests must verify:

```text
write event
  ↓
verify chain
  ↓
PASS

modify protected event
  ↓
verify chain
  ↓
FAIL / INTEGRITY_COMPROMISED
```

Writer and verifier must consume identical canonical hash material/version rules.

## 17. Transaction assertions

Tests must verify atomicity at business level.

Example:

```text
BEGIN
  leave completion
  handover
  movement return
  escort completion
  audit
  outbox
COMMIT
```

If a mandatory step fails, the harness must prove that prohibited partial state does not remain.

Where external notification/document processing occurs after commit, the test must instead prove that the committed domain fact remains valid and the asynchronous work is retryable.

## 18. Idempotency assertions

For a critical command:

```text
Request A + key K
      ↓
commit

Request A + key K
      ↓
REPLAY / same authoritative result
```

But:

```text
Request A + key K
Request B + key K
      ↓
IDEMPOTENCY_CONFLICT
```

Concurrent requests must not produce duplicate authoritative effects.

## 19. Storage/security assertions

The harness must prove:
- protected objects are private;
- arbitrary object keys cannot be requested;
- path traversal is blocked;
- MIME spoofing is detected;
- oversized uploads are rejected;
- revoked objects cannot be downloaded;
- signed URLs are not logged;
- original artifacts are immutable;
- checksums detect tampering.

## 20. Test quality gates

Minimum quality gates:

```text
Typecheck                  PASS
Unit tests                 PASS
Integration tests          PASS
Security tests             PASS
Concurrency tests          PASS
Failure injection          PASS
AI-OFF tests               PASS
Kernel certification tests PASS
```

No test suite may be marked PASS merely because it was not executed. Required states are:

```text
PASS
FAIL
BLOCKED
NOT_RUN
```

`NOT_RUN` is never equivalent to `PASS`.

## 21. Flaky test policy

Flaky tests must not be hidden by automatic retries that convert failures into apparent success.

If retry is permitted for infrastructure noise:
- original failure is recorded;
- retry count is recorded;
- final status preserves evidence of instability;
- repeated flakiness creates a maintenance finding.

Security and concurrency tests should not be silently retried to mask race conditions.

## 22. Test parallelism

Tests may run in parallel only when isolation is guaranteed.

Concurrency tests must intentionally synchronize competing operations to exercise the race condition they are designed to test.

Shared fixtures that can produce cross-test contamination are prohibited.

## 23. Coverage policy

Code coverage is useful but is not the sole acceptance criterion.

A high line-coverage percentage does not prove:
- authorization correctness;
- state-machine integrity;
- concurrency safety;
- source-of-truth integrity;
- audit integrity;
- AI independence.

Certification therefore combines coverage with explicit contract test IDs and negative scenarios.

## 27. P9.11 acceptance criteria

P9.11 is implementation-complete only when:

1. test runner is executable;
2. test environment is isolated;
3. production database access is rejected;
4. synthetic fixtures are versioned;
5. unit/integration/security/concurrency/failure/E2E structures exist;
6. critical personas exist;
7. AI-OFF mode is executable;
8. provider test doubles support failure scenarios;
9. test IDs are stable;
10. test evidence captures commit/environment/result;
11. mandatory negative tests execute;
12. concurrency tests execute deterministically;
13. no test converts `NOT_RUN` to `PASS`;
14. sensitive data is excluded from ordinary test output;
15. certification evidence can be generated.

## 28. Migration and production boundary

- real detainee data in Git;
- production WhatsApp credentials;
- production AI credentials;
- unrestricted export;
- production deployment.

`MIGRATION_FREEZE = TRUE` remains in force.
