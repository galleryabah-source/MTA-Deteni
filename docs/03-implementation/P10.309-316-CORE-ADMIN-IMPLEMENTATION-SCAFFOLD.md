- Classification: **SCAFFOLD_READY**

## Architecture boundary

Implement Core Administration as a domain service behind the existing security/transaction kernel. The domain must not perform direct database writes from UI handlers or create a parallel authorization mechanism.

## Logical components

```text
UI
 ↓
API / Server Action boundary
 ↓
Authorization + scope check
 ↓
Core Administration service
 ├─ detainee aggregate
 ├─ provenance/verification
 ├─ status transition service
 └─ history/event writer
 ↓
Transaction kernel
 ├─ mutation
 ├─ audit
 └─ outbox
```

## Required interfaces

- createDetainee
- getDetainee
- updateAdministrativeFacts
- submitVerification
- verifyFact
- supersedeFact
- transitionStatus
- getDetaineeTimeline
- archiveAdministrativeRecord

All interfaces must accept actor/context and idempotency metadata. Read methods must apply field-level/domain-level filtering before serialization.

## Implementation constraints

No schema migration in this checkpoint. First implementation should target repository-local types, validation, service contracts, synthetic fixtures, and deterministic tests. Persistence adapters remain replaceable until the approved database contract is cleared.

## Acceptance gate

A domain implementation is not considered complete until authorization, validation, history, provenance, idempotency, audit coupling, restricted-field isolation, and failure rollback are covered by automated tests.
