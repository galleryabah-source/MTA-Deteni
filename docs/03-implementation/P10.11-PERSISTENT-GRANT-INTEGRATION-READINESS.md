# P10.11 — Persistent Grant Integration Readiness

## Status

IMPLEMENTED — readiness boundary only. No migration or production database operation is performed.

## Objective

Reconcile the P10.10 persistent grant repository with the existing document, authorization, transaction, audit and outbox boundaries so that a future approved database integration has one unambiguous contract.

## Contract mapping

| Concern | Required contract |
|---|---|
| Document eligibility | Document is already `ISSUED` and retains document/artifact/object/checksum binding. |
| Authorization | Existing deny-by-default authorization remains the decision point; persistent storage cannot grant permission. |
| Grant identity | `grantId` is unique and opaque; no detainee PII is encoded into the grant identifier. |
| Binding | `documentId`, `artifactId`, `artifactSha256`, `objectId`, `actorId`, and `scopeId` are persisted together. |
| Lifetime | `issuedAt` and `expiresAt` are persisted; consume requires `expiresAt > now`. |
| Lifecycle | `ACTIVE → CONSUMED` or `ACTIVE → REVOKED`; terminal states cannot be reused. |
| Single-use | Consumption is one conditional UPDATE and succeeds only when exactly one row is affected. |
| Revocation | Revocation is one conditional UPDATE, ACTIVE-only and actor/scope-bound. |
| Critical transaction | Grant insert + audit + outbox execute on the same PostgreSQL transaction client. |
| Provider isolation | Storage/provider network calls execute only after durable outbox claim and transaction commit. |
| Audit | Grant creation and consumption/revocation remain auditable with correlation/request context. |
| RLS/RBAC | Database policies must preserve application authorization and scope isolation; they must never be treated as a replacement for application authorization. |

## Future database model — contract, not migration

The approved schema must provide at minimum:

- unique `grant_id`;
- foreign/reference binding to the approved document/artifact model where appropriate;
- immutable identity/binding fields after creation;
- `status` constrained to `ACTIVE`, `CONSUMED`, `REVOKED`;
- `issued_at`, `expires_at`;
- nullable `consumed_at` and `revoked_at`;
- indexes supporting lookup by grant identity and lifecycle expiry without weakening authorization predicates;
- database access policy that does not expose grants to anonymous/public actors.

The exact DDL remains intentionally deferred until the database/domain model is approved.

## Integration sequence

`Authorization → ISSUED/Artifact Binding Validation → BEGIN → Grant INSERT → Audit INSERT → Outbox INSERT → COMMIT → Worker Claim → Provider Call → Download → Atomic Grant Consume → Completion Audit`

A provider call must never occur before COMMIT. A grant must never be consumed using a read-then-write sequence.

## Fail-closed requirements

1. Missing authentication/permission/scope/duty/classification/policy → deny.
2. Non-ISSUED document or invalid artifact binding → deny.
3. Grant insert failure → entire critical transaction rolls back.
4. Audit/outbox failure → entire critical transaction rolls back.
5. Consume affected-row count other than exactly one → fail closed.
6. Expired/revoked/consumed/wrong actor/wrong scope/wrong object → consume fails closed.
7. Provider failure after commit → outbox retry/dead-letter policy; grant is not silently reissued.
8. RLS/policy ambiguity → deny until explicitly resolved and tested.

## Migration Freeze

`MIGRATION_FREEZE = TRUE`. This checkpoint creates no DDL, does not apply a Supabase migration, and does not populate a production table. The repository adapter and readiness tests use synthetic data and test doubles only.

## Evidence

P10.11 tests verify that grant creation, audit and outbox share the same transaction client and that the grant transaction contains no provider/network operation. They do not certify real PostgreSQL isolation/concurrency, RLS, storage provider behavior, or production deployment.

GitHub Actions remains an evidence blocker while recent jobs fail before observable steps are exposed. A CI failure without step evidence is not interpreted as an application-test failure and is not converted to PASS.
