## Objective
Provide durable, transactional event handoff from committed domain changes to asynchronous processors without making external providers part of the core transaction.

## Architectural rule
```text
DOMAIN TRANSACTION
      |
      +--> CANONICAL STATE
      |
      +--> AUDIT EVIDENCE
      |
      +--> OUTBOX EVENT
                |
                v
             WORKER
          /     |      \
       WhatsApp Document Reconciliation/other processors
```

The outbox record is written in the same database transaction as the critical domain mutation. External delivery happens after commit.

## Core invariants
1. A required outbox event is committed atomically with its source domain mutation.
2. A provider failure never rolls back an already committed domain fact.
3. Processing is idempotent; retries cannot create duplicate external business effects where the provider supports idempotency.
4. Outbox events carry immutable event identity and correlation metadata.
5. Webhooks are untrusted input and cannot become domain state authority.
6. Outbox workers cannot bypass RBAC/domain authorization to mutate protected state.
7. AI processors are optional and cannot write canonical state through the outbox.
8. Failed processing is observable and recoverable through retry/dead-letter policy.
9. No silent deletion of failed or processed event history.
10. No notification or document provider call occurs before the source transaction commits.

## Event contract
```ts
export type OutboxEvent = {
  eventId: string;
  eventType: string;
  aggregateType: string;
  aggregateId: string;
  correlationId: string;
  causationId?: string;
  payloadVersion: string;
  payload: unknown;
  status: "PENDING" | "PROCESSING" | "SUCCEEDED" | "RETRY" | "DEAD_LETTER" | "CANCELLED";
  attemptCount: number;
  availableAt: string;
  createdAt: string;
};
```

Payload must be a versioned event contract, not an uncontrolled copy of an entire database row.

## Processing lifecycle
```text
PENDING
  ↓
CLAIMED / PROCESSING
  ↓
SUCCEEDED
```

Failure:
```text
PROCESSING
  ↓
RETRY
  ↓
PROCESSING
```

After policy limit:
```text
RETRY
  ↓
DEAD_LETTER
```

Cancellation is policy-controlled and audited. Historical event records are retained according to retention policy.

## Worker claim
Workers must use an atomic claim/lease strategy so two workers do not process the same event concurrently as active owners.

Required concepts:
- lease owner
- lease expiry
- attempt count
- next available time
- worker heartbeat where needed
- stale-lease recovery

A worker crash must not permanently strand an event.

## Idempotency
Each event has immutable `eventId`. Each processor maintains its own processing/idempotency boundary where necessary.

Example:
```text
OUTBOX event E123
   ↓
worker attempt 1
   ↓
provider timeout
   ↓
retry
   ↓
provider receives same logical operation
```

The processor must use a deterministic idempotency reference such as `eventId` and provider-specific idempotency support where available.

## Ordering
Ordering is not globally assumed. If ordering is required, it must be explicit per aggregate/event policy.

Example:
```text
LEAVE_APPROVED
   ↓
DOCUMENT_GENERATE
```

must not be processed as document generation before the authoritative approval event exists.

## Transaction boundary
For a critical command:
```text
BEGIN
  domain mutation
  audit event
  outbox event(s)
COMMIT
```

If outbox persistence fails:
```text
ROLLBACK
```

After commit:
```text
worker → external service
```

## Notification boundary
For WhatsApp:
```text
Leave/Follow-up/Emergency event
        ↓
Notification Event
        ↓
Outbox
        ↓
Recipient Resolution
        ↓
WhatsApp Adapter
        ↓
Provider
```

Provider delivery states remain separate from the source domain state.

`READ` is not equivalent to `ACKNOWLEDGED`.

## Document boundary
For DOCX generation:
```text
Authorized source transaction
        ↓
Document event
        ↓
Outbox
        ↓
Document worker
        ↓
Generate
        ↓
Validate
        ↓
Checksum
        ↓
Private Storage
        ↓
Document Registry
```

Document generation failure must not fabricate an issued document or alter the authoritative leave/escort decision.

## Reconciliation boundary
Domain commits may emit events that trigger reconciliation. Reconciliation detects inconsistency; it does not silently repair facts.

## Retry policy
Retry policy must define:
- retryable vs non-retryable error;
- exponential backoff;
- maximum attempts;
- maximum event age;
- jitter;
- dead-letter transition;
- operator recovery action;
- audit requirements.

Do not retry authorization, validation, malformed payload, or permanent policy errors indefinitely.

## Security
- Payload minimization.
- No secrets in payload.
- Classification metadata carried or resolvable securely.
- Worker authorization is separate from domain actor authority.
- Sensitive payloads must not be emitted to ordinary logs.
- Queue/event inspection is RBAC and classification controlled.
- Provider credentials remain in secret configuration, never event payloads.

## Failure matrix
| Failure | Required behavior |
|---|---|
| Domain transaction fails | No committed domain/outbox effect |
| Outbox insert fails | Rollback critical transaction |
| Worker crash | Lease expires; event recoverable |
| Provider timeout | Retry according to policy |
| Provider permanent error | Retry then dead-letter |
| Duplicate worker claim | One active lease; duplicate processing prevented |
| Duplicate delivery | Processor/provider idempotency prevents business duplication |
| Malformed event | Quarantine/dead-letter + audit |
| Unauthorized worker mutation | Deny/fail closed |
| AI unavailable | Core events continue |
| WhatsApp unavailable | Domain transaction remains valid |
| Storage unavailable | Domain fact remains valid; document event retries |

## Observability
Track:
- pending count;
- processing count;
- retry count;
- dead-letter count;
- oldest pending age;
- processing latency;
- provider latency/failure;
- per-event outcome;
- correlation ID;
- worker health.

Metrics must not expose sensitive payloads.
