# MTA DETENI — P13.601–P13.840

## Purpose

This checkpoint converts the controlled application surface into a coherent operator workbench contract without authorizing production execution.

## P13.601–660 — Operator Workbench

The workbench composes a role-scoped operator surface from the existing dashboard read model. It carries actor identity and correlation identity and rejects unsupported roles or incomplete dashboard identity.

## P13.661–720 — Role-Scoped Navigation

Navigation is derived from the workbench section allow-list. OWNER, ADMIN, EDITOR, REVIEWER and AUDITOR receive different navigation surfaces. Navigation is not an authorization bypass; command authorization remains authoritative.

## P13.721–780 — QR Verification

QR verification is explicitly contextual: `RUDENIM_STAY`, `TEMPORARY_EXIT`, or `DEPORTATION`. A scan requires scan identity, detainee identity, token and validity window. Identity mismatch and expired/out-of-window scans are rejected. A valid scan is verification evidence, not arbitrary data entry.

## P13.781–820 — Movement / Headcount Board

The operational board composes headcount, movement queue, temporary-exit queue and alerts. It is trusted only when reconciliation is `MATCH`. A mismatch produces an untrusted board and blocks trusted-board assertions.

## P13.821–840 — End-to-End Composition

The synthetic acceptance path is:

`Role → Workbench → Navigation → Read Model → QR Verification / Movement / Headcount → Reconciliation → Trusted Operational Board`

All output remains derived state. Operational evidence remains authoritative and rebuildable.
