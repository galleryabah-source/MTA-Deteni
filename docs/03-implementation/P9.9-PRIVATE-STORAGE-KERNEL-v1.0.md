# MTA DETENI — P9.9 Private Storage Kernel v1.0

## Status
CONTRACT COMPLETE / IMPLEMENTATION NOT VERIFIED / MIGRATION FREEZE = TRUE / PRODUCTION = NO-GO

## Objective
Provide a private, controlled, auditable storage boundary for documents, intake artifacts, generated official files, evidence, and other protected binary objects.

The storage layer is an infrastructure capability. It is not a source of truth for business state. Canonical business state remains in the authoritative domain/database records.

## Architectural boundary
```text
Application / Domain Service
          |
          v
     Storage Service
          |
   +------+------+
   |             |
Private Object   Metadata / Registry
   Storage       in PostgreSQL
   |
   +--> checksum / integrity
   +--> encryption
   +--> access policy
   +--> retention
   +--> audit
```

The application must never expose raw object-storage credentials or unrestricted bucket access to the browser.

## Core principles
1. All protected MTA DETENI artifacts are stored in private storage.
2. Storage keys are opaque and server-generated; user input must never become an unrestricted filesystem/object path.
3. Object metadata and business metadata are separated from the binary object.
4. Every protected object has an integrity checksum where technically applicable.
5. Authorization is evaluated server-side before upload, read, download, replace, void, or delete-equivalent operations.
6. Sensitive objects are never served through a public/static directory.
7. Temporary download access is time-limited and purpose-limited.
8. Physical deletion is prohibited for immutable official evidence unless an approved retention/legal policy explicitly permits it; lifecycle actions use archive, revoke, void, or retention-controlled destruction with audit.
9. Original intake artifacts are immutable after acceptance into the evidence chain.
10. Generated official documents are immutable once issued; correction creates a new version/document or controlled supersession.
11. Storage/provider failure must not fabricate or silently change domain facts.
12. AI is not required for storage operation.
13. Storage failures are observable, retryable where safe, and reconciliable.
14. No secret, access token, signed URL, or provider credential is persisted in ordinary logs.

## Storage object classes
Recommended logical classes:

| Class | Examples | Default handling |
|---|---|---|
| INTAKE_ORIGINAL | uploaded PDF/DOCX/image/audio | immutable evidence |
| EXTRACTION_ARTIFACT | OCR/transcript output | linked to source, versioned |
| OFFICIAL_TEMPLATE | approved DOCX template | private, versioned, activation-controlled |
| GENERATED_DOCUMENT | Surat Izin, Surat Tugas, official reports | immutable after issue |
| EVIDENCE | exception/review/reconciliation evidence | protected, audited |
| EXPORT_ARTIFACT | controlled CSV/XLSX/PDF/DOCX | temporary/expiring by policy |
| SYSTEM_ARTIFACT | diagnostics/non-sensitive technical artifacts | policy controlled |

Actual classification must be determined by policy and data content, not merely filename or extension.

## Storage key convention
Use a server-generated key such as:
```text
mta-deteni/{environment}/{class}/{tenant-or-scope}/{yyyy}/{mm}/{object-id}/{random-object-name}
```

Requirements:
- no raw detainee name in the key;
- no nationality in the key;
- no document number unless policy explicitly permits and risk is assessed;
- no original filename as the authoritative storage key;
- no `../`, path traversal, absolute paths, or arbitrary bucket names from clients;
- object IDs must be generated server-side;
- environment/bucket separation must prevent development/test objects from being mixed with production objects.

The exact provider-specific key format is an implementation detail and must not become part of domain logic.

## Storage service contract
```ts
export interface PrivateStorageService {
  put(request: StoragePutRequest): Promise<StoragePutResult>;
  getMetadata(objectId: string, context: StorageAccessContext): Promise<StorageObjectMetadata>;
  createTemporaryDownload(request: TemporaryDownloadRequest): Promise<TemporaryDownloadResult>;
  revoke(objectId: string, reason: string, context: StorageAccessContext): Promise<void>;

  verifyIntegrity(objectId: string, context: StorageAccessContext): Promise<StorageIntegrityResult>;

```

There must be no generic `get(path)` operation exposed to untrusted callers.

## Upload pipeline
```text
REQUEST
  ↓
AUTHENTICATION
  ↓
AUTHORIZATION + SCOPE + CLASSIFICATION
  ↓
REQUEST SIZE / CONTENT-TYPE CHECK
  ↓
QUARANTINE
  ↓
BINARY / MIME / STRUCTURE VALIDATION
  ↓
MALWARE / SECURITY SCAN (IF AVAILABLE)
  ↓
CHECKSUM
  ↓
STORE PRIVATE OBJECT
  ↓
REGISTER METADATA
  ↓
AUDIT
  ↓
AVAILABLE
```

A failed validation must leave the object unavailable to ordinary application users.

## MIME and file validation
Do not trust the browser-supplied `Content-Type` or filename extension.

Validation should include, according to object class:
- maximum size;
- detected MIME type;
- magic-byte/signature validation;
- permitted extension/type mapping;
- parser/structure validation for DOCX/PDF/images/audio as applicable;
- malformed archive detection for container formats;
- filename normalization;
- dangerous content rejection;
- malware scanning where infrastructure supports it;
- decompression-bomb/resource exhaustion controls;
- image dimension limits;
- PDF page/object/resource limits where appropriate.

DOCX must be validated as an actual supported Office Open XML document, not merely as a file named `.docx`.

## Quarantine
New untrusted uploads should enter `QUARANTINED` before becoming `AVAILABLE`.

Quarantine rules:
- inaccessible to ordinary download endpoints;
- limited administrative/service access;
- scan/validation result recorded;
- failed scan → `REVOKED` or dedicated rejected state according to policy;
- retry is idempotent;
- quarantine objects have retention limits;
- audit records preserve who/what caused status changes.

## Encryption
Where supported by the deployment architecture:
- encryption at rest must be enabled for protected storage;
- provider-managed encryption is acceptable only when it satisfies approved security requirements;
- highly restricted objects may require stronger key-management controls;
- encryption keys/secrets are managed outside source code;
- key rotation must not silently invalidate existing objects;
- key-management events are auditable.

Transport must use TLS for storage access and application-to-storage communication.

## Authorization model
Storage authorization follows:
```text
AUTHENTICATION
  AND ROLE
  AND PERMISSION
  AND SCOPE
  AND CLASSIFICATION
  AND RESOURCE
  AND PURPOSE/POLICY
  AND OBJECT STATE
```

Examples:
- a user may view a detainee record but not automatically download every attached document;
- a reviewer may access evidence required for a review task but not unrelated L4 artifacts;
- an auditor may inspect audit-linked evidence subject to classification and scope;
- export access does not imply raw-object access;
- Super Admin does not automatically bypass classification or policy.

## Temporary download
Downloads should use a server-authorized, short-lived access mechanism.

Flow:
```text
User
 ↓
Authenticated request
 ↓
Authorization decision
 ↓
Scope/classification/purpose check
 ↓
Object state check
 ↓
Create short-lived download grant
 ↓
Download
 ↓
Audit
```

Requirements:
- short expiration;
- least privilege;
- one object/purpose at a time where practical;
- no reusable bearer token stored in application logs;
- no public permanent URL;
- download event includes actor, object, purpose, correlation ID, and result;
- expired/revoked grants must fail.

## Signed URL policy
If provider signed URLs are used:
- generated only after authorization;
- expiration must be policy-controlled;
- scope must be limited to the intended object and operation;
- signed URL itself is a secret and must not be logged;
- users must not be able to request arbitrary storage keys;
- revoked/expired objects must not receive new grants.

## Original artifact immutability
For D4 intake:
```text
ORIGINAL ARTIFACT
    ↓
CHECKSUM
    ↓
IMMUTABLE STORAGE OBJECT
    ↓
EXTRACTION / REVIEW / CANONICAL PROVENANCE
```

The original file cannot be overwritten through normal application operations.

A new upload is a new object with a new identity/checksum and a new provenance link.

## Official document integrity
For generated official documents:
```text
AUTHORIZED SOURCE
  ↓
GENERATE
  ↓
VALIDATE
  ↓
SHA-256
  ↓
PRIVATE STORAGE
  ↓
DOCUMENT REGISTRY
  ↓
ISSUE
```

Issued documents must preserve:
- document ID/number;
- template version;
- source transaction ID;
- immutable data snapshot;
- checksum;
- storage object ID;
- generation/issue timestamp;
- generating/issuing actor or service;
- correlation ID;
- lifecycle status.

Storage availability is required for a document to be considered successfully issued under the document contract.

## Checksum and integrity verification
SHA-256 is the baseline checksum for stored binary integrity unless a formally approved stronger mechanism is required.

Verification must detect:
- object missing;
- checksum mismatch;
- metadata/object mismatch;
- unexpected size change;
- storage provider corruption/error.

An integrity mismatch must create an auditable finding and must not silently replace the object.

## Retention and lifecycle
Storage lifecycle must be policy-driven.

Recommended states:
```text
QUARANTINED → AVAILABLE → ARCHIVED → EXPIRED
                     ↘ REVOKED
```

For official/immutable evidence, destruction requires an approved retention/legal policy and an auditable destruction event. Ordinary application users must never have a generic delete capability.

Retention policy must define:
- object class;
- retention period;
- legal/administrative hold interaction;
- archive transition;
- expiration behavior;
- destruction authority;
- evidence preservation requirements;
- audit retention.

## Replacement/versioning
Do not overwrite a protected object in place.

For a corrected template/document/evidence artifact:
```text
OBJECT v1
  ↓
NEW OBJECT v2
  ↓
RELATION / SUPERSEDES EVENT
  ↓
AUDIT
```

The previous object remains traceable unless a formally authorized retention policy requires destruction.

## Storage/database consistency
Storage metadata and database state can become temporarily inconsistent because object storage is external to the database transaction.

Therefore:
- object registration must be idempotent;
- generated object identity must be stable;
- outbox/reconciliation mechanisms must detect missing object, orphan object, checksum mismatch, and registry mismatch;
- no business state is silently changed because a provider call failed;
- document issuance follows the separate document transaction/worker contract;
- cleanup of orphaned objects is policy-controlled and audited.

Recommended reconciliation findings:
- `STORAGE_OBJECT_MISSING`
- `STORAGE_METADATA_MISSING`
- `STORAGE_CHECKSUM_MISMATCH`
- `STORAGE_ORPHAN_OBJECT`
- `STORAGE_STATUS_MISMATCH`
- `STORAGE_CLASSIFICATION_MISMATCH`
- `STORAGE_SOURCE_LINK_BROKEN`

## Path traversal and object-key security
Never concatenate client-controlled input into storage paths.

Explicitly reject or neutralize:
- `../` and `..\\`;
- absolute paths;
- encoded traversal sequences;
- null bytes;
- control characters;
- unexpected Unicode normalization cases;
- provider-specific bucket/path escape syntax.

The preferred defense is not sanitization alone: clients should provide an object ID or logical purpose, while the server resolves the actual storage key.

## Resource exhaustion controls
Storage endpoints must enforce:
- maximum request body size;
- per-user and per-scope upload rate limits;
- maximum file size by class;
- maximum number of files per operation;
- parser timeouts;
- extraction/scan resource limits;
- bounded concurrent processing;
- retry budgets.

## Logging and observability
Log metadata needed for operations without exposing protected content.

Allowed examples:
- object ID;
- object class;
- size;
- checksum;
- operation;
- result;
- correlation ID;
- latency;
- provider error code.

Do not log:
- file contents;
- signed URLs;
- provider credentials;
- access tokens;
- raw highly restricted metadata unless specifically authorized.

## Failure matrix
| Failure | Required behavior |
|---|---|
| Authentication failure | Deny; do not reveal object existence unnecessarily |
| Authorization failure | Deny; audit |
| Scope mismatch | Deny; audit |
| Classification denied | Deny; audit |
| Upload too large | Reject before persistence where possible |
| MIME mismatch | Quarantine/reject |
| Malware/security scan failure | Keep unavailable; audit |
| Storage provider unavailable | No fabricated success; retry/recover according to policy |
| Checksum mismatch | Integrity failure; block/flag object; no silent replacement |
| Download grant expired | Deny |
| Object revoked | Deny |
| Object missing | Controlled error + reconciliation finding |
| Database metadata missing | Controlled error + reconciliation finding |
| Worker crash | Recover through idempotent job/lease strategy |
| AI unavailable | Storage remains fully operational |
| Signed URL leakage attempt | Never log; revoke/expire according to policy |

## Security invariants
- `STO-INV-01`: protected artifacts are never public by default.
- `STO-INV-02`: browser clients never receive storage credentials.
- `STO-INV-03`: client input cannot select arbitrary storage keys.
- `STO-INV-04`: every protected object has an authorization boundary.
- `STO-INV-05`: classification is enforced server-side.
- `STO-INV-06`: original intake artifacts are immutable.
- `STO-INV-07`: issued official documents are immutable.
- `STO-INV-08`: checksum mismatch is detectable and auditable.
- `STO-INV-09`: permanent public URLs are not used for protected objects.
- `STO-INV-10`: temporary download grants are time-limited.
- `STO-INV-11`: signed URLs are never logged.
- `STO-INV-12`: generic delete is not exposed to ordinary users.
- `STO-INV-13`: Super Admin does not bypass classification/policy automatically.
- `STO-INV-14`: storage provider failure cannot fabricate a business fact.
- `STO-INV-15`: storage operations carry correlation/audit context.
- `STO-INV-16`: environment isolation prevents cross-environment object access.
- `STO-INV-17`: object replacement creates a new immutable object identity.
- `STO-INV-18`: orphan/missing objects are reconciliable.
- `STO-INV-19`: AI is not required for storage operation.
- `STO-INV-20`: storage access fails closed when critical authorization context is unavailable.
