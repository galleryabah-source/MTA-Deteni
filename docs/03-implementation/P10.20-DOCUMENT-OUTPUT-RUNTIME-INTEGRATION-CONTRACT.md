# P10.20 — Document Output Runtime Integration Contract

## Status

PREPARED — deterministic runtime orchestration contract; synthetic-only, no production database execution.

## Objective

Bind the existing document renderer, lifecycle authorization, private artifact storage and persistent artifact-grant boundary into one deterministic runtime orchestration path for the two required MVP Word outputs.

## Runtime sequence

`authorize → validate document state → validate template manifest → render DOCX → compute SHA-256 → persist artifact metadata → transition/issue under SoD → append audit → enqueue outbox → commit → issue secure grant → provider/download`

No external provider/network operation is permitted before transaction commit. Grant creation must reference the committed artifact identity and checksum.

## Output contract

Supported document kinds are exactly:

- `TEMPORARY_EXIT_PERMISSION`;
- `ESCORT_ASSIGNMENT_LETTER`.

The runtime rejects unknown document kinds and arbitrary template paths. Template selection is by approved manifest identity/version, not by user-supplied filesystem location.

## Authorization and lifecycle

The runtime must establish an authenticated operational context and validate permission, scope, duty, classification and resource state before issuance. Lifecycle transitions remain explicit and fail closed. Approval and issuer responsibilities remain separated where required.

A Super Admin flag does not itself confer operational authority and cannot bypass the operational authorization boundary.

## Artifact binding

The final `.docx` bytes are the integrity source. The runtime records opaque artifact ID, document ID, template ID/version, SHA-256, classification, storage state and correlation/causation identifiers. Any mismatch blocks issuance/download.

## Transaction boundary

Document metadata mutation, required audit append and required outbox enqueue must share the same transaction context for the critical mutation. A transaction failure must leave these components uncommitted together. Provider/network delivery is an after-commit concern.

## Persistent handoff

After commit, secure download is mediated by the persistent grant contract. The grant binds artifact/document/hash/object/actor/scope and expiry. Consume is atomic and single-use. Replay, expiry, revocation and context mismatch deny access.

## Idempotency

Repeated requests with the same canonical operation identity and equivalent payload must converge deterministically. A conflicting payload under the same idempotency identity must be rejected rather than creating a second official artifact or grant.

R20.2 unauthorized/wrong-scope/inactive context is denied;
R20.3 invalid template manifest or unknown document kind is denied;
R20.4 deterministic synthetic input produces stable DOCX checksum;
R20.5 issuance requires required approval/SoD and final artifact binding;
R20.6 artifact metadata, audit and outbox use the expected transaction context;
R20.7 injected transaction failure produces no partial official issuance;
R20.8 post-commit grant binds the exact artifact/hash and operational context;
R20.9 first consume succeeds exactly once;
R20.10 replay/wrong actor/wrong scope/wrong object/expired/revoked consume is denied;
R20.11 conflicting idempotency payload is denied;
R20.12 provider/network call occurs only after commit;
R20.13 evidence contains only opaque synthetic operational metadata.

## Hard stops

Block the operation when authorization context, template identity, artifact checksum, lifecycle state, approval/SoD, transaction context, secure grant binding or evidence safety is incomplete. `SKIPPED_BY_SAFETY_GATE` is not a PASS result.
