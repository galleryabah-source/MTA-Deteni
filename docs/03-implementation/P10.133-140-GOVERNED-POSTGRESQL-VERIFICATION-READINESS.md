# P10.133–P10.140 — Governed PostgreSQL Verification Readiness

## Purpose

Prepare the MTA DETENI persistence layer for a future controlled PostgreSQL verification without executing a live database operation during Migration Freeze.

## Verification prerequisites

1. A non-production PostgreSQL target explicitly approved for controlled verification.
2. A governance decision that permits the verification scope and records the operator, time window, rollback owner, and evidence destination.
3. `MIGRATION_FREEZE` remains TRUE unless governance explicitly clears the freeze for the exact operation; no implicit freeze lift is allowed.
4. `AI_ENABLED=false` for the certification path.
5. Synthetic fixtures only; no production detainee data.
6. Provider/network calls disabled inside the critical transaction and tested only as post-commit behavior.
7. Independent evidence capture available for SQL result counts, transaction outcome, test identity, environment flags, and hashes.

## P10.133–P10.134 — Transaction evidence

Every controlled transition must expose an observable `BEGIN -> domain mutation -> audit/outbox -> COMMIT` path, with `ROLLBACK` on any failure. Audit and outbox callbacks must use the same transaction client. A successful application response without transaction evidence is insufficient for certification.

## P10.135 — Concurrent consume

Two or more consumers targeting the same ACTIVE grant must race against the same database row predicate. Exactly one transaction may observe `affected_rows = 1`; all losing attempts must fail closed. The verification must record both winning and losing outcomes.

## P10.136 — Expiry

The database predicate must enforce `expires_at > now` at transition time. An expired grant must not become CONSUMED even when application-level timing is favorable.

## P10.137 — Authority scope

Actor, scope, and object predicates are part of the atomic transition. Wrong actor, wrong scope, or wrong object must yield zero affected rows and must not change grant state.

## P10.138 — Revoke race

Concurrent consume/revoke activity must permit only one valid ACTIVE transition. A second transition against an already-consumed or revoked row must fail closed.

## P10.139 — Isolation controls

No provider/network call is permitted before successful COMMIT. Migration freeze and AI-off state must be captured as evidence dimensions. Any violation aborts the verification run.

## P10.140 — Abort and rollback conditions

Abort immediately on unexpected schema mutation, production-data detection, credential leakage, provider invocation inside a transaction, authorization bypass, affected-row ambiguity, failed audit/outbox coupling, failed rollback, or evidence-integrity failure. Preserve diagnostic evidence; do not continue after a safety-gate violation.

## Evidence package

The future governed run should produce:

- immutable run identifier and commit SHA;
- environment safety flags;
- test matrix and per-scenario result;
- SQL/affected-row observations without sensitive payloads;
- transaction outcome (`COMMIT`/`ROLLBACK`);
- audit-chain evidence (`eventCount`, `headHash`);
- provider isolation evidence;
- migration-freeze evidence;
- artifact hashes and evidence-manifest hash;
- explicit final classification: PASS, FAIL, or BLOCKED.

## Current boundary

This document is a readiness specification only. It does not authorize or perform migrations, schema changes, live database writes, provider calls, or production certification. Governance clearance and a controlled non-production target are required before live verification.
