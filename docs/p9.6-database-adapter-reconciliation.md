## Live schema reconciliation

Verified tables:
- mta_detainees
- mta_placements
- mta_movements

- mta_audit_events
- mta_profiles
- mta_scopes
- mta_profile_scopes
- mta_qr_registry
- mta_ai_config
- mta_ai_jobs

Key findings:
1. mta_detainees.scope_id is NOT NULL; scope is mandatory at persistence level.
2. Placement, movement and leave records reference detainees through detainee_id.
3. Documents contain revision/integrity fields and JSON payload.
4. AI configuration and AI jobs are separate persistence concerns.
5. mta_audit_events contains actor/request/correlation/occurrence metadata but no hash-chain material required by P9.5.
6. QR registry is security-sensitive and is intentionally outside the generic CRUD table allow-list.

## Runtime boundary decision

P9.6 does not introduce a second database access path.

The Edge Function remains the privileged server boundary. The browser continues to use the runtime adapter and production API. This avoids exposing PostgreSQL credentials or service_role to the browser and avoids duplicate persistence paths.

The generic domain API currently supports detainees, placements, movements, leaves and documents. QR registry and AI configuration/job operations use dedicated governed endpoints.

## Acceptance

**P9.6 = PASS WITH ARCHITECTURAL DEFERMENT**

The adapter contract, lifecycle, role governance, migration freeze, schema reconciliation and production transport boundary are consistent.

A direct PostgreSQL implementation is deliberately deferred because the current production architecture already has a server-side Supabase boundary. Adding a second direct DB adapter without a concrete runtime consumer would create duplicate persistence paths.
