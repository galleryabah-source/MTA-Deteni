# MTA DETENI — End-to-End Audit P13.5241–5600

**Audit scope:** blueprint, roadmap, governance, domain contracts, application contracts, security barriers, document/reporting controls, QR/movement controls, local/LAN continuity, recovery, testing and evidence/release semantics.

**Audit basis:** repository state on `phase-p12.961-13.200` at Foundation v1.60 / P13.5240, plus the implemented contracts through P13.5240. This audit distinguishes implemented contract/code from independently observed execution.

## 1. Executive conclusion

MTA DETENI has reached a strong **architecture-and-governance contract maturity**. The design is coherent around domain ownership, least privilege, immutable history, controlled document generation, QR contextual verification, offline safety and evidence-driven release.

The principal risk has shifted: the project is no longer primarily missing conceptual controls. The dominant risk is **contract-to-runtime convergence**. A large portion of the recent implementation defines rigorous acceptance boundaries, but those boundaries still require actual non-production execution evidence before they can be treated as operationally certified.

**Overall assessment: AMBER — structurally strong, execution evidence pending.**

## 2. What is strong

### Governance and architecture

- Governance-first positioning is explicit.
- Production remains unauthorized and migration freeze remains active.
- Repository is synthetic-only by policy.
- AI is disabled and cannot be treated as a decision maker.
- Separation between substantive leadership oversight and technical authorization administration is explicit.
- Restricted PERKES data is treated as a separate access domain.

### Domain boundaries

The Master Blueprint establishes clear ownership:

- RAP — registration, administration and reporting.
- PERKES — health records/workflows.
- KAMTIB — placement, movement, headcount, temporary exit, escort and operational QR.
- SUBBAG_TU — escort-document administration.
- HEAD_RUDENIM — oversight/directive layer without direct operational editing.

These boundaries should remain stable unless governance formally changes them.

### Core workflow

Temporary exit remains a distinct lifecycle from deportation. The intended chain is request → validation → approval → exit letter → escort → execution → return → result/event → timeline/audit.

### Evidence discipline

The newer P13 contracts correctly refuse to infer PASS from source presence. `NOT_RUN` is not PASS, unexpected control identities are rejected, and final evidence is intended to be based on observed execution.

## 3. Critical findings

### F-01 — Runtime evidence is the current release bottleneck — HIGH

The repository defines the observation sequence, but the latest status remains OBSERVATION_PENDING. GitHub Actions runs for the latest implementation have not been observable through the available repository evidence. Therefore typecheck, JavaScript regression, TypeScript tests, browser smoke, LAN, report rendering, recovery and security must not be described as certified.

**Recommendation:** stop expanding abstract acceptance contracts unless a discovered runtime gap requires one. Execute the existing matrix first.

### F-02 — Domain contract naming drift — HIGH

The shared domain contract uses `LEADERSHIP`, while the governance model consistently uses `HEAD_RUDENIM`. This is a semantic drift risk: authorization, audit, navigation and policy code can eventually disagree about the same actor/domain.

**Recommendation:** establish one canonical domain vocabulary and add a compatibility mapping only if historical code requires it. Prefer `HEAD_RUDENIM` for the substantive role/domain terminology if that is the approved governance term.

### F-03 — Integrity primitives are not cryptographic everywhere — HIGH

The local continuity integrity checksum uses FNV-1a, which is non-cryptographic. That is acceptable as a lightweight corruption-detection mechanism but not as an authenticity or tamper-resistance primitive. The report/document design separately calls for SHA-256 integrity.

**Recommendation:** explicitly classify FNV-1a as non-security checksum and reserve SHA-256/HMAC/signature mechanisms for security-sensitive integrity and authenticity claims.

### F-04 — Disaster-recovery rehearsal contract is presence-based — MEDIUM/HIGH

The current rehearsal contract verifies that required step names exist, but it does not itself bind each step to an execution observation, timestamp, backup identity, restore artifact, integrity result, replay output or human sign-off evidence.

**Recommendation:** connect every DR step to the same evidence ledger used by P13.5041+ so DR readiness is evidence-backed rather than checklist-presence-backed.

### F-05 — Document fidelity is still an evidence boundary — HIGH for MVP output

The blueprint makes the DOCX outputs core MVP deliverables. The implementation has strong template/source-binding contracts, but exact visual reproduction of the supplied daily guard report still requires actual rendering and visual review against the approved source template.

**Recommendation:** make report rendering a concrete execution workstream, not another abstract contract. Capture source-template identity, renderer version, artifact hash, page count, geometry/element evidence and human visual acceptance.

### F-06 — Data model remains intentionally logical — HIGH governance importance

The Master Blueprint explicitly states that candidate entities are a logical model and must not become a migration command before D1/D2 approval.

**Recommendation:** perform a dedicated data-contract audit before any schema work: entity ownership, keys, cardinality, lifecycle, history strategy, classification, retention, provenance, deletion/archival and cross-domain references.

## 4. Structural findings

### S-01 — CI scope is narrow

The repository workflow runs Node setup, dependency installation, typecheck, JavaScript regression and TypeScript domain tests. This is useful but does not certify browser, LAN, DOCX rendering, recovery or security behavior.

**Recommendation:** keep the domain CI deterministic and add separate controlled acceptance jobs only when their runtime dependencies are reproducible and synthetic.

### S-02 — TypeScript configuration does not include tests

The current `tsconfig.json` includes `src/**/*`, while TypeScript tests are executed through `tsx`. This means `npm run typecheck` does not act as a compiler check over the test source tree.

**Recommendation:** introduce a deliberate test tsconfig or otherwise make test compilation/type validation explicit without coupling production build configuration to test-only dependencies.

### S-03 — Persistence integration remains the major architectural implementation frontier

The project has extensive application contracts for transactions, idempotency, authorization, outbox, read-model projection and recovery, but the audit must still distinguish these contracts from a fully exercised durable PostgreSQL runtime.

**Recommendation:** once D1/D2 are formally approved, implement persistence behind the existing ports and execute against an explicitly approved non-production database. Do not migrate production.

### S-04 — Idempotency and projection edge cases require focused verification

Known design cautions include separate in-memory idempotency state in the controlled non-production transaction contract and potential same-checkpoint re-projection behavior.

**Recommendation:** create concurrency/retry tests for duplicate command, same idempotency key/different fingerprint, projection retry, checkpoint replay and outbox duplication.

## 5. Security audit direction

The architecture correctly emphasizes deny-by-default, least privilege, separation of duties, restricted health data, CSRF/CORS/rate limiting, audit integrity and production barriers.

The next security review should be execution-oriented:

1. authentication/session boundary;
2. authorization decision for every mutation;
3. cross-domain access denial;
4. HEAD_RUDENIM operational mutation denial;
5. sensitive export/download control;
6. audit append-only behavior;
7. audit tamper detection;
8. CSRF/CORS/rate limiting;
9. secret handling;
10. dependency and supply-chain checks;
11. backup confidentiality;
12. local LAN trust/pairing/revocation.
