# E6.14 — PostgreSQL Persistence Design v1.0

## Status

Contract/design only. **No SQL schema and no migration are authorized by this document.**

## Objective

Provide a durable implementation boundary for the MTA DETENI Document Engine without changing domain contracts or allowing persistence concerns to leak into business logic.

## Transaction boundary

The following state must be committed atomically when they belong to one terminal business operation:

`Document state + artifact binding + numbering register + audit event + idempotency commit + outbox event`

If any mandatory component fails, the transaction must roll back as a unit. No partial success may be reported to the caller.

## Concurrency controls

### Lifecycle

Use a persisted current-state check. A transition must match the expected `from` state. Concurrent requests attempting the same transition must not both succeed.

### Numbering

Number allocation is scoped by the defined register key. Production persistence must enforce uniqueness at the database level and serialize allocation/commit so concurrent requests cannot receive the same number.

A failed transaction must not make an already-observed issued number silently reusable.

### Idempotency

The idempotency key and request fingerprint form one logical uniqueness boundary. The same key with a different fingerprint is rejected. A committed key returns the original result rather than repeating the business operation.

Crash recovery requires durable ownership/lease semantics; an in-progress record must never be treated as safely retryable merely because time elapsed.

### Outbox

The outbox event must be inserted in the same transaction as the state change it represents. Delivery happens after commit. Processing requires durable claim/lease semantics so a worker crash cannot permanently strand an event in PROCESSING.

## Audit integrity

Audit events are append-only. The production adapter must preserve the existing hash-chain semantics and ensure the audit event describing a transaction is committed with that transaction. The audit repository must not become a separate best-effort write path.

## Isolation

`READ_COMMITTED` is the baseline candidate. Operations that allocate scarce identifiers or require serialization may use stronger locking/isolation where required by the final SQL design. The adapter must document each escalation rather than globally selecting SERIALIZABLE without evidence.

## Required database-level guarantees

The eventual schema must enforce, at minimum:

- immutable primary identifiers;
- unique document IDs;
- unique artifact IDs;
- unique document-to-artifact binding;
- unique artifact-to-document binding;
- unique idempotency key;
- numbering register uniqueness by register scope/number;
- immutable audit event identity and sequence constraints;
- durable outbox event identity;
- foreign-key relationships matching the approved domain chain;
- timestamps with explicit timezone semantics.

Exact table names, indexes, constraints, SQL types, ORM models and migration files remain deferred.

## Restricted-domain requirements

Persistence must not weaken authorization. PERKES data remains restricted independently of application UI. RLS and service-layer authorization must be designed together. Database connectivity is never an authorization bypass.

## Object storage

Document artifact bytes should use an immutable object-storage abstraction. Database records retain the binding, integrity hash and metadata required to retrieve and verify the artifact. Storage deletion/retention must be policy-controlled.

## Crash recovery

Recovery is reconciliation-first:

1. detect ambiguous state;
2. obtain authoritative transaction evidence;
3. complete or compensate only through an authorized workflow;
4. preserve auditability;
5. never silently delete, overwrite, or reuse identifiers.

## Gate before schema/migration

Before E6.15/E6.16 production implementation, approve:

- exact identifier model;
- final lifecycle terminal/rejection/void semantics;
- authorization evidence model;
- audit transaction linkage;
- numbering scope and uniqueness;
- idempotency lease/recovery model;
- outbox lease/recovery model;
- RLS/unit isolation model;
- retention and restricted-data policy.
