# E6.15 — RBAC/RLS Persistence Contract v1.0

## Security objective

PostgreSQL must never become an authorization bypass. Application authorization and database row-level isolation are complementary controls.

## Mandatory controls

- deny by default;
- authenticated subject required;
- unit/organizational scope enforced;
- ownership scope enforced where applicable;
- restricted and highly restricted domains require additional policy controls;
- restricted access requires declared purpose;
- service-layer authorization remains mandatory;
- SUPER_ADMIN does not receive an implicit database bypass;
- audit access is explicit and separately controlled;
- exports/downloads are treated as sensitive actions;
- break-glass access requires explicit policy and audit evidence.

## Unit isolation

A user operating in unit A must not read or modify unit B resources merely by changing a resource identifier. Cross-unit access requires an explicitly authorized role/policy such as an approved audit scope.

## PERKES boundary

PERKES is a restricted domain. Persistence controls must prevent ordinary application roles from reading PERKES records through direct API/database paths. Purpose limitation and least-privilege access remain mandatory.

## SUPER_ADMIN boundary

SUPER_ADMIN is an administrative application role, not a database bypass mechanism. Administrative authorization must still pass through the same auditable policy boundary.

## PostgreSQL design requirements

The eventual implementation should use RLS policies tied to trusted session/request context. Client-controlled unit IDs, role claims, ownership values, and classification values must not be accepted as authoritative authorization evidence.

The service layer must establish trusted authorization context before persistence operations. SECURITY DEFINER functions, if used, must be narrowly scoped and reviewed for search_path, privilege, and ownership implications.

## Data access modes

The persistence contract distinguishes READ, WRITE, APPROVE, ISSUE, EXPORT, and ADMIN. These modes must not collapse into a generic CRUD permission.

## No migration yet

This contract intentionally defines security requirements without creating SQL, tables, policies, or migrations. Those artifacts require a subsequent approved database design.
