# P9.8 — Transactional Outbox

Status: IMPLEMENTED / DATABASE-VERIFIED / PENDING APPLICATION E2E

## Purpose

P9.8 establishes the transactional outbox boundary immediately after the P9.7 durable transaction/idempotency kernel.

Required path:

HTTP mutation → Authentication → Authorization → Request hash + Idempotency → PostgreSQL transaction → Domain mutation → Audit event → Outbox event → Idempotency response → HTTP response

The domain mutation, mandatory audit record, outbox event, and idempotency completion are committed in the same PostgreSQL transaction.

## Production object

Private schema:

- `mta_internal.outbox_events`

The table is not exposed to `anon` or `authenticated`. Service-role access is explicit.

## Event contract

Each event contains:

- `event_id`
- `event_type`
- `aggregate_type`
- `aggregate_id`
- `payload`
- `idempotency_key`
- `occurred_at`
- `status`
- `attempts`
- `available_at`
- `locked_at`
- `published_at`
- `last_error`
- `created_at`

Initial status is `PENDING`.

## Atomicity

P9.7 now performs domain mutation, audit write, outbox insert, and idempotency completion inside one PostgreSQL transaction. Any exception rolls all four effects back.

The outbox has a unique `idempotency_key`, so a replay returns the stored response before the mutation path executes and cannot create a duplicate outbox event.

## Scope

P9.8 establishes reliable event persistence. It does not yet certify a publisher/worker or external delivery target.

The next operational layer is a governed dispatcher with claim/lease semantics, bounded retries, backoff, poison-event handling, acknowledgement, and consumer-side idempotency.
