# P9.7-F — Canonical Transaction + Idempotency Contract Reconciliation

## Decision

The canonical application execution identity is:

- requestId
- correlationId
- transactionId
- idempotencyKey

The persistence transaction contract additionally requires:

- actorId
- aggregateId

Therefore P9.7 treats these as two layers rather than creating a second competing context:

`ExecutionContext` = request/transaction continuity identity.

`PersistenceOperationContext` = persistence authorization/audit identity derived from the execution context plus actor and aggregate identity.

## Production mapping

The current production Edge Function already carries:

- X-Request-Id
- X-Correlation-Id
- Idempotency-Key
- authenticated actor user ID

The production PostgreSQL mutation RPC receives requestId, correlationId, actorUserId and idempotencyKey inside its audit payload.

The aggregate/resource identity is derived from the target resource and resulting row.

Status: **RECONCILED FOR PRODUCTION BRIDGE**

## Transaction identity

A transactionId is an application-level continuity identifier. The current production RPC does not expose a separate transactionId parameter because its mutation, audit, outbox, and idempotency operations execute inside one PostgreSQL function invocation.

Therefore:

- transaction boundary = PostgreSQL RPC invocation
- transaction identity = application correlation metadata until a concrete direct PostgreSQL adapter is introduced
- no new RPC parameter is authorized in this migration-free P9.7 step

Status: **ACCEPTED WITH EXPLICIT BOUNDARY**

## Idempotency identity

The idempotency key remains distinct from requestId and correlationId.

Rules:

1. requestId identifies an individual HTTP request.
2. correlationId groups related execution activity.
3. transactionId identifies application transaction continuity.
4. idempotencyKey identifies the mutation replay identity.
5. request hash binds the idempotency key to one exact mutation intent.

A repeated idempotency key with a different request hash is a conflict, not a replay.

Status: **CANONICAL**

## No schema change

This reconciliation requires no database migration and no production schema mutation.

## Remaining implementation gate

Before P9.7 certification, deterministic tests must prove:

- execution-context continuity
- transaction commit/rollback semantics
- same-key/same-hash replay
- same-key/different-hash conflict
- audit/outbox/idempotency response coupling
- invalid context rejection
- production bridge request-to-RPC identity mapping

The direct PostgreSQL adapter remains a separate architecture item and is not introduced merely to satisfy this reconciliation.
