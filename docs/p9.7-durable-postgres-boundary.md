# P9.7 Durable PostgreSQL Transaction Boundary

Status: IMPLEMENTED / PENDING APPLICATION E2E CERTIFICATION

## Governance

The migration freeze was opened specifically for P9.7 because the existing in-memory idempotency Map could not provide restart-safe or concurrent durable semantics.

No unrelated schema change is included.

## Production boundary

Write requests for the five domain resources are now routed by `mta-api` through:

`HTTP mutation → RBAC → canonical request hash → idempotency key → PostgreSQL function → domain mutation + audit → idempotency response → HTTP response`

The PostgreSQL boundary is:

- `mta_internal.idempotency_keys` — durable idempotency record.
- `mta_internal.execute_idempotent_mutation(...)` — private transaction kernel.
- `public.mta_execute_idempotent_mutation(...)` — service-role-only wrapper used by the Edge Function.
- Allowed mutations: INSERT, UPDATE, DELETE.
- Allowed tables: `mta_detainees`, `mta_placements`, `mta_movements`, `mta_leaves`, `mta_documents`, plus `mta_ai_jobs` for controlled AI execution.
- UPDATE/DELETE require the primary-key `id` predicate.
- Unknown tables/columns and immutable `id`/`created_at` updates are rejected.
- Audit insertion occurs in the same PostgreSQL transaction as the mutation.
- Idempotency completion is written in the same transaction.
- Any exception rolls back mutation, audit, and idempotency claim together.

## Idempotency semantics

1. First request with a new key executes the mutation.
2. Same key + same request hash returns the stored response with `replayed=true`.
3. Same key + different request hash returns `P9_7_IDEMPOTENCY_CONFLICT`.
4. A failed transaction leaves no durable idempotency record, so a retry can safely execute again.
5. The browser API client propagates `Idempotency-Key`, `X-Request-Id`, and `X-Correlation-Id`.

## Remaining certification

P9.7 is not marked fully certified until application-level E2E proves the deployed HTTP mutation path with an authenticated user, including retry/replay and conflict behavior. Live browser/network verification is currently unavailable in this execution environment.

## Security boundary

The internal idempotency table is in a non-exposed schema. The public wrapper is executable only by `service_role`; `anon`, `authenticated`, and `PUBLIC` execution are revoked. The Edge Function remains the authenticated/RBAC gateway.

Supabase recommends least-privilege function grants and private schemas for internal database objects; this implementation follows that boundary.
