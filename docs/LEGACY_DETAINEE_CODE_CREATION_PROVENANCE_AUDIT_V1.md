# Legacy Detainee Code Creation Provenance Audit V1

Date: 2026-10-02

## Purpose

Determine the actual provenance of newly created legacy detainee `code` values before any attempt is made to remove the remaining creation dependency.

This audit does not generate, replace, rename, or drop `code`.

## Executive result

**CANONICAL LEGACY CODE GENERATOR NOT ESTABLISHED.**

The inspected application path shows that a new legacy `code` is currently supplied as compatibility input rather than generated by the canonical NID generator.

Observed production-oriented path:

```
operator/UI input
      ↓
mta-domain-commands-v1.createDetainee(options.code)
      ↓
mta-production-state-adapter-v1 create
      ↓
mta-api POST /detainees
      ↓
idempotent mutation boundary
      ↓
public.mta_detainees.code
```

The canonical NID generator is separate and is not a source for legacy `code`.

Therefore:

```
NID  = canonical generated operational identity
code = legacy compatibility value with unresolved creation provenance
DROP = BLOCKED
```

## Evidence inventory

### P-01 — Main UI is an explicit source of new code

File:

- `web/mta-app-runtime-full.js`

Observed behavior:

- the create/edit dialog contains a field labeled `Kode Legacy (compatibility)`;
- the create form reads `formData.get('code')`;
- create flow passes the supplied `code` into the detainee command;
- the synthetic seed also contains hard-coded legacy code values.

Classification:

**USER-ENTERED COMPATIBILITY SOURCE**

The UI is therefore not merely displaying a generated identifier. It is an input source for new legacy code values.

### P-02 — Domain create contract accepts caller-supplied code

File:

- `web/mta-domain-commands-v1.js`

Observed behavior:

- `createDetainee(state, options)` reads `options.code`;
- creation rejects an empty code;
- duplicate code is checked against existing detainees;
- the created detainee object persists the supplied code.

Classification:

**CALLER-SUPPLIED WRITE CONTRACT**

No canonical legacy generator is present in this command.

### P-03 — Production adapter forwards code on create

File:

- `web/mta-production-state-adapter-v1.js`

Observed behavior:

- normal update payloads no longer contain code after PR #295;
- the create path explicitly retains `clean.code`;
- create therefore preserves the compatibility creation dependency.

Classification:

**PRODUCTION WRITE FORWARDER**

The adapter does not generate the value.

### P-04 — Generic production API does not generate legacy code

File:

- `supabase/functions/mta-api/index.ts`

Observed behavior for detainee POST:

- caller-supplied `nid` is rejected;
- `entry_year` is validated and mapped to `entry_year`;
- no canonical assignment of `code` occurs in the API boundary;
- the request body continues through the generic idempotent mutation boundary.

Classification:

**API COMPATIBILITY WRITE SURFACE**

The server-side API is not an authoritative legacy-code generator.

The database therefore remains responsible for accepting the compatibility value supplied by the caller path, subject to the existing schema constraints.

### P-05 — Production database generator is NID-only

The production NID migration established the canonical generator:

- `mta_detainee_nid_seq`;
- `mta_assign_canonical_nid()`;
- INSERT-time NID generation;
- UPDATE-time NID immutability.

The inspected canonical generator has no dependency on legacy `code`.

Classification:

**NO LEGACY CODE GENERATOR IDENTIFIED**

### P-06 — Backup/restore preserves existing code

File:

- `supabase/functions/mta-api/index.ts`

Observed behavior:

- backup reads `mta_detainees` using `select("*")`, which includes `code`;
- backup manifest is schema version 1;
- restore passes the complete detainee payload into the backup restore transaction.

Classification:

**RECOVERY / REPRODUCTION SOURCE**

Backup/restore can reproduce existing legacy code values. This is not a new-code generator, but it is a provenance path that must be versioned before physical retirement.

## Provenance matrix

| Source / path | Can introduce new code? | Generates code? | Status |
|---|---:|---:|---|
| Main UI create form | Yes | No | Active compatibility source |
| Domain create command | Yes | No | Active compatibility contract |
| Production adapter create | Yes | No | Active forwarder |
| Generic detainee API POST | Yes | No | Active compatibility write surface |
| NID generator | No | NID only | Canonical, unrelated to code |
| Backup restore | Can restore code | No | Recovery dependency |
| Synthetic seed | Seeds fixed examples | No | Non-production fixture |
| Database inspected generator | No | No code generator found | No authoritative legacy generator |

## What is proven

1. New legacy code is currently caller-supplied.
2. The main UI is an explicit source of the value.
3. The domain command does not generate the value.
4. The production adapter does not generate the value.
5. The generic API does not generate the value.
6. The canonical database generator generates NID, not legacy code.
7. Backup/restore preserves legacy code values.
8. No authoritative legacy-code generator was identified in the inspected application/database paths.

## What is not yet proven

The following remain outside the proven boundary:

- external clients not represented in the repository;
- undocumented operational/import scripts outside the inspected paths;
- historical/manual database procedures;
- external integrations that may submit legacy `code`;
- whether an operational business rule exists outside the repository that dictates how a new legacy code must be chosen.

Therefore this audit does **not** authorize immediate removal of `code` from the production create contract.

## Engineering decision

Do not invent a new legacy generator.

The safe boundary is:

```
CREATE:
  NID      → system generated
  code     → temporary compatibility input

UPDATE:
  NID      → immutable
  code     → immutable / DENY on mutation

RETIREMENT:
  blocked until external + operational provenance is closed
```

## Required next gate

The next engineering gate is **Legacy Code Creation Compatibility Strategy V1**.

It must choose, based on operational evidence, one of these documented outcomes:

1. **Retain compatibility input temporarily**, with an explicit owner and retirement date; or
2. **Migrate creation to an authoritative legacy-code source** only if that source is independently proven; or
3. **Declare legacy code non-authoritative and remove it from the normal create contract** after a compatibility/recovery version transition.

No option should create a second identity generator.
