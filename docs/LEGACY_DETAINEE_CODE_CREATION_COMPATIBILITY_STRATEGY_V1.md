# Legacy Detainee Code Creation Compatibility Strategy V1

Date: 2026-10-02

## Purpose

Define the safe compatibility strategy for legacy detainee `code` after the Creation Provenance Audit established that no authoritative legacy-code generator is currently proven.

This strategy does not change production schema or data.

## Decision

**RETAIN TEMPORARY COMPATIBILITY INPUT.**

The system must not invent a new legacy-code generator.

Until an authoritative replacement source is independently proven, legacy `code` remains a compatibility field required by the existing production creation contract.

The canonical identity remains NID.

```
NID
  = canonical operational identity
  = system generated
  = immutable

code
  = legacy compatibility reference
  = caller supplied during temporary creation window
  = immutable after creation
  = not canonical identity
```

## Why this option is selected

The provenance audit established:

1. the current UI/domain path supplies new `code` values;
2. the production adapter forwards the value on create;
3. the generic API does not generate it;
4. the canonical database generator generates NID, not `code`;
5. backup/restore preserves existing `code`;
6. no authoritative legacy-code generator was established in the inspected application/database paths;
7. external and undocumented operational sources remain unverified.

Removing `code` from CREATE now would therefore break the existing NOT NULL compatibility contract without a proven replacement.

Creating a new generator would introduce a second identity-generation seam.

Neither action is justified by the available evidence.

## Compatibility contract V1

### CREATE

Allowed temporarily:

```
CREATE detainee
  ├── entry_year → required
  ├── NID        → generated by canonical DB boundary
  └── code       → compatibility input
```

The caller may supply an existing-format legacy code during the compatibility window.

The system must not reinterpret `code` as canonical identity.

### UPDATE

Closed:

```
UPDATE code → DENY
```

Existing `code` values remain immutable after creation.

### READ

NID-first:

- operational identity uses NID;
- UI/detail/report/QR presentation should prefer NID;
- `code` may remain available only where required for compatibility/recovery.

### BACKUP / RESTORE

The existing backup contract remains compatibility-bearing.

Before `code` can be removed, backup/restore must receive an explicit schema-version transition proving that:

- old backups remain identifiable;
- restore behavior is deterministic;
- the legacy field is either preserved as compatibility metadata or safely transformed;
- no restored record loses canonical NID identity.

## Ownership boundary

During the temporary compatibility window:

- NID owns operational identity;
- `code` owns no operational identity semantics;
- callers may provide `code` only for compatibility;
- mutation of an existing `code` is denied;
- no new code-generation algorithm may be introduced under this strategy;
- no downstream feature may use `code` as a substitute for NID.

## Exit criteria

The compatibility window may close only when all of the following are proven:

### G1 — External provenance closure

No external or undocumented production caller requires `code` as an authoritative creation input.

### G2 — Replacement contract

A production create contract exists that does not require caller-supplied legacy `code`.

### G3 — Backup version transition

Backup/restore has a versioned contract that no longer depends on `code` for canonical identity.

### G4 — Zero active operational consumers

Repository/runtime scan proves no active operational consumer treats `code` as identity.

### G5 — Production observation

Production evidence shows new detainee creation succeeds without a legacy `code` dependency.

### G6 — Recovery evidence

A backup/restore rehearsal proves canonical NID survives the compatibility transition.

Only after G1–G6 are green may the project proceed to a retirement migration.

## Retirement sequence

```
Compatibility Strategy V1
        ↓
external / operational dependency closure
        ↓
NID-first create contract
        ↓
backup / restore schema transition
        ↓
zero-code operational consumer scan
        ↓
production create + recovery evidence
        ↓
compatibility window closure
        ↓
DROP UNIQUE(code)
        ↓
DROP code
```

No step above authorizes a physical drop by itself.

## Explicit non-goals

This gate does not:

- generate new legacy codes;
- rename `code`;
- remove `code` from production schema;
- change existing production rows;
- change NID generation;
- merge legacy code into NID;
- claim external dependency is zero.
